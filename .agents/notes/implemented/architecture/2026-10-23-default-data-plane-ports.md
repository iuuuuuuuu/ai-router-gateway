# Agent Note: 数据面默认端口上调到 38080 / 38443

Status: implemented

## Problem

数据面默认监听 `0.0.0.0:8080` + `0.0.0.0:8443`。这两个是开发机与容器环境里最常被别的服务先占用的端口（各类 dev server、代理、示例服务都默认 8080），冲突时网关启动直接 bind 失败，用户看到的是一个起不来的进程，而不是一条可理解的配置提示。

## Decision

数据面默认值改为 `0.0.0.0:38080`（HTTP）与 `0.0.0.0:38443`（HTTPS）。管理面默认仍是 `127.0.0.1:9090` —— 桌面客户端与所有探针都按 9090 探测网关是否已就绪，改它就要同步改客户端启动逻辑与全部探针，收益不成比例。

改动落在四处默认值来源，缺一处就会出现「新库用新端口、重启后又变回旧端口」的分裂：`server/src/config.rs` 的 `d_http_addr` / `d_https_addr`、`server/src/main.rs` 的兜底元组、`client/src/store.ts` 的 `normalize()`、`client/src/pages/Settings.vue` 的提示与 placeholder。文档同步 README、`docs/AGENTS.md`、`docs/方案.md`。

**只改默认值，不迁移存量配置。** `listen` 一旦写进 `gateway.db` 就是该库的既定值，新默认值只对**全新库**生效；已部署实例继续用原端口，要换必须显式改配置并重启（监听地址改动本就不热更新）。

## Alternatives considered

- **保持 8080 但启动失败时给出明确报错。** 最强理由是它对存量用户零影响，而端口冲突的根因本来就是「环境里已有服务」。否掉的原因是报错只能事后解释，用户仍要手工找一个空闲端口并改配置；换默认值是把冲突概率直接降下来。
- **改用 1024–49151 之间的常见高端口（如 18080）。** 最强理由是更好记。否掉的原因是该区间被各类开发服务大量占用，常见度本身就是风险；落在 38080/38443 这类冷门区间，冲突概率更低且仍在合法非特权端口内。
- **连管理面一起换到高端口。** 最强理由是三个端口风格统一。否掉的原因是客户端 `spawn_gateway`（`client/src-tauri/src/main.rs`）和全部真机探针都硬编码探测 9090，改它会把「一条默认值」变成「一次跨组件契约变更」，而管理面只绑回环、本来就没有对外暴露需求。

## Consequences

- 收益：全新安装的数据面落在冷门端口，被本地其他服务抢占的概率显著下降。
- 代价：**存量配置不会自动迁移**。已在 8080 上跑起来的实例，升级后仍是 8080 —— 想让新默认生效必须删库重建或在「设置」页手工改端口并重启。
- 代价：用户文档、第三方接入示例里的 `:8080` 需要一并改，否则照着旧文档连不上新库。
- 边界：本次没有做「端口被占用时自动挑一个空闲端口」。绑定失败依旧是启动失败，变化只是默认值更不容易撞。

## Verification

- `cd server && cargo test --release --locked` 实跑：**202 passed / 0 failed**（配置默认值不改变 I4 预算等式，`6 × 25000 + 3000 = 153000 ≤ 180000`）。
- 全新数据目录启动 release `gw-server.exe`：`gateway.log` 打印 `data plane http on http://0.0.0.0:38080` 与 `https on https://0.0.0.0:38443`；真请求 `http://127.0.0.1:38080/healthz` 与 `https://127.0.0.1:38443/healthz`（自签，`-k`）都返回 `ok`，旧端口 `:8080` 无监听。
- 存量库（复制用户真实 `gateway.db` 到临时目录启动，不动原库）：仍打印 `8080` / `8443` 并返回 `ok`，而 `:38080` 无监听 —— 证明「不迁移存量」成立，不是我以为它不迁移。
- 客户端 `node node_modules/vite/bin/vite.js build` 通过；`Settings.vue` 只改了提示与 placeholder，取值仍来自 `state.cfg.listen`，不会覆盖配置里的实际端口。
