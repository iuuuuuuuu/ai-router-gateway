# Agent Note: CI 只跑笔记门禁与服务端测试，真机验收仍留在本机

Status: implemented

## Problem

`docs/DECISIONS.md` 的 D09 原本的结论是「仓库没有 `.github/`、没有 CI 工作流」，理由是核心承诺（I1 提交前零字节、失败零外漏、提交后不重发）只有在真实实例上跑真实字节流才能证伪，而探针需要 Windows + WebView2 + 本机网关。

这条理由对**真机验收**成立，对**另外两类门禁**不成立：

- `cargo test --release` 的假上游全部绑 `127.0.0.1:0`（`server/tests/support/mod.rs`），走真 socket 但不依赖外网、不依赖 GUI，云端 Linux/Windows 跑得出同样结果。
- Agent Notes 的三线校验是纯文本检查，连编译都不需要。

于是 D09 的代价被放大了：「提交前是否跑过 `cargo test`」完全靠纪律，没有自动化兜底。一次忘记跑、或跑了旧工作树，远端不会有任何信号。这恰恰是本仓库明令禁止的「假绿」形态 —— 门禁看起来存在，实际没验证到东西。

D09 自己写了翻案条件：「探针能在无 GUI 环境稳定复现核心断言时，把**那部分**搬进 CI；GUI 真机验收仍留在本机」。前两类门禁已经满足这个条件。

## Decision

仓库有 `.github/workflows/ci.yml`，两个 job，各自独立、互不依赖：

| job | 运行环境 | 跑什么 |
|---|---|---|
| `agent-notes` | `ubuntu-latest` | `node .agents/skills/agent-notes/scripts/verify-agent-note-tree.ts` / `-format.ts` / `verify-archived-agent-notes.ts`，再跑 `node tools/verify-notes-gates.mjs` |
| `server-tests` | `windows-latest` | `cargo test --release --locked`，`working-directory: server` |

触发：`push` 到 `main` 与所有 `pull_request`。

**范围边界（硬约束）**：

- **GUI 真机验收不进 CI，也不许用本工作流冒充它。** 需要真实 `gw-server.exe` + 真实 Tauri 客户端 + 真实数据面请求的断言，仍按 `docs/TESTING.md` 在本机跑。CI 绿只证明「服务端集成测试过了 + 笔记结构合规」，不证明 I1 在真实实例上成立。
- **不加前端构建 job。** `client/` 的 vite build 是编译门禁，不驱动真实路径；把它塞进 CI 会让「CI 绿」显得比实际更强。前端改动的验证仍是本机探针。
- **不加任何 `|| true`、`continue-on-error`、`if: always()` 式的软化。** 三个笔记脚本各占一步，任一步非零退出即 job 失败。串成一行用 `;` 会让中间步骤的退出码被最后一步覆盖，所以刻意分三步写。
- `--locked` 是刻意的：`Cargo.lock` 与 `Cargo.toml` 不一致时 CI 直接失败，而不是在云端静默解析出一组新依赖。本机开发允许 `cargo update`，CI 不允许。

**元门禁 `tools/verify-notes-gates.mjs`（入库）**：CI 的最后一步不是「再跑一次校验」，而是**逐条对三条校验脚本做故障注入** —— 未知分类目录、文件名不合规、死链、缺 `## Alternatives considered`、implemented 里出现 `## Proposal`、Status 与 lifecycle 不符、缺 manifest、封印后篡改、归档头部布局错，共 9 条注入，每条都必须变红；另有一份未注入副本作为对照必须为绿。它还含一条自检：把脚本换成恒 `exit 0` 的桩，注入器必须能识别出来。

这一步的存在理由是 `docs/AGENTS.md` §5.1：一条恒 `exit 0` 的校验与一条真的校验，在「跑绿了」上长得一模一样。没有它，CI 前三步全绿也可能什么也没验证。脚本只用 Node 内置模块，在系统临时目录建副本、跑完即删，不含本机路径与网络。

**两个环境选择**：

- `windows-latest` 而不是 `ubuntu-latest`：服务端产物是 Windows exe，`cargo test --release` 在本机就是 Windows 上跑绿的；换 Linux 会引入一个从没人验证过的平台，绿了也不代表本机绿。
- Node 24（`actions/setup-node`）：Node 22.6+ 起原生剥离 TS 类型，24 是 LTS。仓库根没有 `package.json`，**不需要 npm install**，脚本零依赖直接跑。实测 v24.11.0 与 v25.9.0 均可。skill 副本目录下的 `package.json` 只声明 `"type":"module"`，用来消掉 ESM 解析警告，不是依赖清单。

**归档封印的基线**：`AGENT_NOTE_ARCHIVE_BASE_REF` 取 `github.event.pull_request.base.sha || github.event.before`。默认值 `HEAD` 在干净检出上等于「manifest 与自身对比」，查不出 append-only 违规 —— 用 HEAD 等于没查。新分支推送时 `before` 是全 0，`git show` 失败，脚本会跳过 append-only 段（封印与磁盘的哈希校验仍执行）。

**与 D09 的关系**：这是 D09 的**部分翻案**，不是全盘推翻。D09 关于「真机验收不能搬上云端」的结论仍然成立并继续有效；被推翻的只是「所以整个仓库一条 CI 都不要」这个推论。

## Alternatives considered

- **在 `windows-latest` 上跑全部三类门禁，包括真机探针。** 最强理由是它一次性消灭「靠纪律」的缺口，让每次 push 都有最接近本机的证据。否掉的原因是探针硬编码了本机端点与真实上游密钥（见 `docs/DECISIONS.md` D10），入库即泄密；而且探针要拉起 Tauri 客户端与 WebView2，云端无头环境跑不稳定 —— 一个时绿时红、且绿的时候也不代表真实字节流的门禁，正是 D09 点名要避免的假绿。
- **把 `cargo test --release` 放 `ubuntu-latest`，省一半运行时间。** 最强理由是 Linux runner 更便宜更快，Rust 测试本应跨平台。否掉的原因是这个仓库**从未在 Linux 上验证过**：`server/tests/loopguard.rs` 用 `std::env::temp_dir()`、集成测试依赖 Windows 的路径与时序假设，首次上 Linux 很可能一上来就红，而那种红不指向产品缺陷，只会逼人加 `#[cfg]` 豁免 —— 豁免就是假绿的入口。等有人真的需要 Linux 支持时再开，那时它是被验证过的目标平台。
- **只接笔记门禁，`cargo test` 继续靠本机纪律（即 D09 原文不动）。** 最强理由是 `cargo test --release` 在本机跑一次要几分钟且吃 4.6GB target，云端重复跑是浪费。否掉的原因是它保留了最大的那个缺口：服务端集成测试是主门禁，它没有自动化兜底意味着「忘记跑」和「跑过了」在远端完全同形。笔记门禁本身很轻，单独接它等于只给次要门禁上锁。
- **用 `npx tsx` 跑笔记脚本而不是 Node 原生。** 最强理由是 skill 原文就是这么写的，且 tsx 对 TS 语法的兼容面更宽。否掉的原因是多一个网络依赖：CI 每次要下载 tsx，离线或 registry 抖动时门禁直接不可用，而这三个脚本只用了类型注解与 `interface`，Node 24 的原生剥离足够。本地临时对比过两条路径，输出一致。

## Consequences

- **收益**：主门禁第一次有了自动化兜底 —— 推上远端就能知道 `cargo test --release` 是红是绿，不必相信「我跑过了」。笔记结构同理：漏写头块、文件名日期不合规、归档被篡改，都会在 PR 上直接红。
- **收益**：`--locked` 让依赖漂移在 CI 上暴露，而不是等到发版时产物与锁文件对不上。
- **代价**：`windows-latest` 的排队与冷编译比 Linux 慢；首次跑要编译整个 release profile（`opt-level="z"` + `lto=true` + `codegen-units=1`），耗时以十分钟计。`Swatinem/rust-cache` 缓解重复构建，但 `lto` 让缓存命中率不如 debug 构建。
- **代价**：CI 绿容易被误读成「可以发了」。本仓库的发版前置仍是完整实机测试 + 逐行自审（`docs/RUNBOOK.md` §1.1），CI 不替代其中任何一项。这条写在 workflow 顶部注释里，就是为了让人在改它时先看见。
- **已知上限**：笔记门禁只查结构，不查语义；`cargo test` 只覆盖假上游集成层，不覆盖真实上游行为。两者合起来仍小于本机真机验收。
- **重访信号**：若真机探针被改造成无 GUI、参数化、不含本机凭据（D10 里 `start-client.mjs` 是先例），可以把**那部分**搬进 CI；若服务端真的要支持 Linux，再加一个 Linux job 并让它先在本机 WSL 上跑绿。

## Verification

- `actionlint .github/workflows/ci.yml` 退出码 0。
- `cd server && cargo test --release --locked` 本机实跑：**202 passed / 0 failed / 0 ignored**，13 个测试目标，退出码 0。
- `node tools/verify-notes-gates.mjs` 本机实跑：9 条故障注入全部按预期变红、2 条对照为绿、元注入识别出恒 `exit 0` 的桩，退出码 0。这条命令本身也会在 CI 里跑，所以「门禁能变红」这件事每次都被重新证明，而不是只在接入时验过一次。
- `--locked` 分支的故障注入：往 `server/Cargo.toml` 加一个未写入 `Cargo.lock` 的依赖，`cargo metadata --locked` 以 101 退出（`cannot update the lock file … because --locked was passed`）；复原后退出码回到 0。
- 未在本机跑的部分（诚实标注）：workflow 本身只在 GitHub runner 上真跑过才算验证过，本机只做了 `actionlint` 静态校验与逐条命令的等价实跑。首次 push 后需要在 Actions 页面确认两个 job 都为绿。
