# Agent Note: CI 只跑等价复现的门禁，真机验收留在本机

Status: implemented

## Problem

`docs/DECISIONS.md` 的 D09 原本的结论是「仓库没有 `.github/`、没有 CI 工作流」。理由是可证的：核心承诺（I1 提交前零字节、失败零外漏、提交后不重发）只有在真实实例上跑真实字节流才能证伪，而真机探针需要 Windows + WebView2 + 本机网关，云端跑不出同等证据。

但这条理由只对**真机验收**成立，对另外两类门禁不成立：

- `cargo test --release` 的假上游全部绑 `127.0.0.1:0`（`server/tests/support/mod.rs`），走真 socket 但不依赖外网与 GUI。
- 笔记三线校验是纯文本检查，连编译都不需要。

于是 D09 的代价被放大了：主门禁**没有自动化兜底**。「提交前是否跑过 `cargo test`」完全靠纪律，一次忘记跑、或跑了旧工作树，远端不会有任何信号 —— 这本身就是一种假绿。

D09 自己写了翻案条件：「探针能在无 GUI 环境稳定复现核心断言时，把**那部分**搬进 CI」。前两类门禁满足这个条件。

## Decision

仓库有 `.github/workflows/ci.yml`，两个独立 job：

| job | 运行环境 | 跑什么 |
|---|---|---|
| `agent-notes` | `ubuntu-latest` | 笔记三线校验 + `node tools/verify-notes-gates.mjs`（元门禁） |
| `server-tests` | `windows-latest` | `cargo test --release --locked`，`working-directory: server` |

触发：`push` 到 `main` 与所有 `pull_request`。

**范围边界（硬约束）**：

- **GUI 真机验收不进 CI，也不许用本工作流冒充它。** 需要真实 `gw-server.exe` + 真实 Tauri 客户端 + 真实数据面请求的断言，仍按 [docs/TESTING.md](../../../../docs/TESTING.md) 在本机跑。
- **不加前端构建 job。** `client/` 的 vite build 是编译门禁，不驱动真实路径。
- **不加 `|| true` / `continue-on-error` / `if: always()`。** 三个笔记脚本各占一步：串成一行用 `;` 会让中间步骤的退出码被最后一步覆盖。
- **`--locked` 是刻意的。** `Cargo.lock` 与 `Cargo.toml` 不一致时 CI 直接失败，而不是在云端静默解析出一组新依赖。

**两个环境选择**：

- `windows-latest` 而非 `ubuntu-latest`：服务端产物是 Windows exe，本机就在 Windows 上跑绿；换 Linux 会引入一个从没验证过的平台，绿了也不代表本机绿。
- Node 24：原生剥离 TS 类型（22.6+ 起），仓库根没有 `package.json`，**不需要 npm install**。

**归档封印的基线**取 `github.event.pull_request.base.sha || github.event.before`。默认值 `HEAD` 在干净检出上等于「manifest 与自身对比」，查不出 append-only 违规 —— 用 HEAD 等于没查。

**与 D09 的关系**：这是**部分翻案**。D09 关于「真机验收不能搬上云端」的结论仍然成立；被推翻的只是「所以整个仓库一条 CI 都不要」这个推论。

## Alternatives considered

- **在 `windows-latest` 上跑全部三类门禁，包括真机探针。** 最强理由是它一次性消灭「靠纪律」的缺口，每次 push 都有最接近本机的证据。否掉的原因是探针硬编码了本机端点与真实上游密钥（`docs/DECISIONS.md` D10），入库即泄密；且探针要拉起 Tauri 客户端与 WebView2，云端无头环境跑不稳定 —— 一个时绿时红、绿时也不代表真实字节流的门禁，正是 D09 点名要避免的假绿。
- **把 `cargo test --release` 放 `ubuntu-latest`，省一半运行时间。** 最强理由是 Linux runner 更便宜更快，Rust 测试本应跨平台。否掉的原因是这个仓库从未在 Linux 上验证过：`server/tests/loopguard.rs` 用 `std::env::temp_dir()`、集成测试带 Windows 的路径与时序假设，首次上 Linux 很可能一上来就红，那种红不指向产品缺陷，只会逼人加 `#[cfg]` 豁免 —— 豁免就是假绿的入口。
- **只接笔记门禁，`cargo test` 继续靠本机纪律。** 最强理由是 `cargo test --release` 本机跑一次要几分钟、吃 4.6GB target，云端重复跑是浪费。否掉的原因是它保留了最大的缺口：服务端集成测试是主门禁，「忘记跑」与「跑过了」在远端完全同形。

## Consequences

- **收益**：主门禁第一次有了自动化兜底。推上远端就知道 `cargo test --release` 是红是绿，不必相信「我跑过了」。笔记结构同理：漏写头块、文件名不合规、归档被篡改都会在 PR 上直接红。
- **收益**：CI 首次上线就兑现了价值 —— 抓到一个本机永远绿的时区依赖测试缺陷，见 [主机时区无关性](../bug-fix/2026-10-17-timezone-portability.md)。
- **代价**：`windows-latest` 的排队与冷编译比 Linux 慢；首次跑要编译整个 release profile（`opt-level="z"` + `lto=true` + `codegen-units=1`），实测约 9 分钟。`Swatinem/rust-cache` 缓解重复构建，但 `lto` 让缓存命中率不如 debug 构建。
- **代价**：CI 绿容易被误读成「可以发了」。发版前置仍是完整实机测试 + 逐行自审（`docs/RUNBOOK.md` §1.1），CI 不替代其中任何一项。
- **已知上限**：笔记门禁只查结构不查语义；`cargo test` 只覆盖假上游集成层，不覆盖真实上游行为。两者合起来仍小于本机真机验收。
- **重访信号**：若真机探针被改造成无 GUI、参数化、不含本机凭据（`tools/start-client.mjs` 是先例），把**那一条**搬进 CI；服务端真要支持 Linux 时再加 Linux job，但必须先在 WSL 上跑绿。
