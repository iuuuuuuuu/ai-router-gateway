# Agent Note: 决策笔记树与门禁的落地形态

Status: implemented

## Problem

仓库从 2026-10-17 起有两套决策记录：`docs/DECISIONS.md` 的 `D01`–`D17`（冻结只读）与 `.agents/notes/` 笔记树。笔记树建起来了，但一直是**空的** —— 只有 24 个 `{lifecycle}/{class}` 空目录和 `.gitkeep`。

空树带来三个实际问题：

1. **门禁形同虚设。** 三条校验脚本对 0 篇笔记恒绿，「目录没乱」是唯一还能被检查的东西；笔记该怎么写、写成什么样，没有任何在仓库里的范例可参照。
2. **规范版本落后。** `.agents/skills/agent-notes/` 的副本是 2026-10-17 的，而上游已到 0.4.1（2026-10-18）：新增了 `## 后果与边界`、`## 其他做法` 两个节名别名，支持 CommonMark 尖括号链接目标，`archived/AGENTS.md` 不再被当成归档笔记校验，并明确要求「写完笔记必须跑验证」。旧副本会把这些合法写法判红。
3. **元门禁的自证范围不全。** `tools/verify-notes-gates.mjs` 只覆盖旧的校验规则；上面这些新行为一条都没有反向用例，等于新逻辑未经证明就被信任。

## Decision

**笔记树采用「事件驱动、按需落笔」的填充策略**：不为了填满而写，每篇笔记对应一个真实发生过的非平凡决定。当前已落地的笔记见下方「现有笔记」。

**规范以随仓库分发的副本为准，版本钉在 `0.4.1`**（`.agents/skills/agent-notes/.synced-version`）。副本与上游逐字节一致，只额外包含两个文件：

- `package.json`（`{"type":"module"}`）：让 Node 按 ESM 解析脚本，消掉 `MODULE_TYPELESS_PACKAGE_JSON` 警告，不是依赖清单。
- `README.md`：说明本地路径与上游文档里 `.agents/skills/write-notes-like-deepseek/` 的差异，以及升级方式。

**写完或改完任何笔记必须跑验证**，三条命令在仓库根执行（Node 24+ 原生剥离 TS 类型，无需 `npm install`）：

```bash
node .agents/skills/agent-notes/scripts/verify-agent-note-tree.ts
node .agents/skills/agent-notes/scripts/verify-agent-note-format.ts
node .agents/skills/agent-notes/scripts/verify-archived-agent-notes.ts
```

**元门禁 `tools/verify-notes-gates.mjs` 覆盖 0.4.1 的全部新增行为**，每条都是双向的：

| 新增行为 | 正向（新版必须绿） | 反向（必须红） |
|---|---|---|
| CommonMark 尖括号链接目标（链接目标两端包一对尖括号） | 指向存在的笔记 → 绿 | 剥掉尖括号后仍判死链 → 红 |
| `## 后果与边界` 作为 `Consequences` 别名 | 接受 → 绿 | — |
| `## 其他做法` 作为备选方案别名 | 接受 → 绿 | — |
| `archived/AGENTS.md` 跳过 | 不校验头部 → 绿 | — |

**「旧版会红、新版才绿」是逐条实证的，不是推断。** 用 `git show 9d355b2:` 取出旧版三个脚本，在同一个合成样本上分别跑新旧两版，确认旧版的失败来自**真正的校验逻辑**（死链、缺节、头部布局），而非脚本加载失败。

**什么必须写**：改了行为、架构、跨文件契约、流程与工具链、测试策略、落盘 / 网络 / 配置格式，或其他维护者日后可能重访的决定。**什么不写**：纯格式化、错别字、无歧义重命名、不改行为的样式与依赖补丁、版本打标、常规 CRUD、单模块内看 diff 即懂的修复。判不准时从严。

## Alternatives considered

- **保持空树，等有真实决定时再写第一篇。** 最强理由是笔记的价值来自真实性，为填而填会产生没人维护的陈列品，反而稀释信噪比。否掉的原因是本轮确实发生了两个非平凡决定（CI 范围、时区可移植性），它们已经改变了仓库的约束条件却不留痕；而且空树让「笔记该怎么写」没有任何可参照的范例，下一个人只能从 SKILL.md 的抽象描述里猜。
- **不升级副本，只补笔记。** 最强理由是副本落后不影响当前能跑通，升级要重新验证四条新行为，成本不为零。否掉的原因有两层：一是这就是一条非平凡决定（工具链版本变更），按规范本身必须留痕；二是旧副本会把 0.4.1 定义的合法写法判红，等于让门禁与新规范打架，而门禁一旦开始误报就会被绕过 —— 那是假绿的入口。
- **把笔记树填满全部 6 个 class 各一篇，显得结构完整。** 最强理由是示例覆盖面广，后来人能看到各分类的写法。否掉的原因是这需要编造没发生过的决定，直接违反「没有过的选项不要编」；`rejected/` 尤其危险，编出来的被否方案会让后来人误以为某条路已经试过并被否定。

## Consequences

- **收益**：笔记树从「结构合规的空壳」变成「有真实范例、且范例本身通过门禁」的状态。三条校验脚本第一次有实际内容可校验，元门禁也从 9 条注入扩到 15 条检查。
- **收益**：副本升到 0.4.1 后，`## 后果与边界`、`## 其他做法`、尖括号链接、`archived/AGENTS.md` 这四种写法不再被误判，门禁与规范一致。
- **代价**：副本与上游仍会漂移，升级靠人工。`0.4.1` 这个版本号是手工同步的产物，它只证明「同步那一刻一致」，不证明未来一致。
- **代价**：元门禁的「旧版会红」验证依赖 `git show <commit>:` 取历史版本，脚本写死在临时脚本里、没有入库。这是一次性取证，不是可持续的门禁；下次升级不会自动重跑这项对照。
- **已知上限**：门禁只校验结构（头块、必备节、分类、文件名、链接、封印），**不校验语义** —— `## Alternatives considered` 里写的是不是真考虑过的方案、`## Decision` 是不是现在时、正文是不是简体中文，全部靠人。「门禁全绿」不等于「笔记写得好」。

## Verification

- 四条门禁命令在仓库根执行均 exit 0（`0 note(s)` 是当前笔记数为 0 时的输出，补入笔记后数字随之变化）。
- `node tools/verify-notes-gates.mjs` → **15 条检查全 PASS**（2 条对照绿 + 9 条注入红 + 4 条 0.4.1 正向绿 + 1 条元注入自检），exit 0。
- 新旧对照实证：用 `git show 9d355b2:` 取出旧版三个脚本，与新版在同一合成样本上对比，4 个新用例全部呈现「旧版 exit=1 / 新版 exit=0」，且旧版报错内容分别是死链、缺 `Consequences`、缺 `Alternatives`、`AGENTS.md` 头部不合规 —— 都是真实校验失败。
- **一次被自己抓到的假验证**：首次做新旧对照时，旧版脚本全部以 `MODULE_NOT_FOUND` 失败，看起来「旧版变红」，实则脚本根本没跑起来。原因是旧脚本放在 MSYS 的 `/tmp` 路径下，Windows 的 Node 打不开。修正为 Windows 可见路径、并加一条「旧版对新版都能跑空树」的 sanity 前置，对照才成立。
