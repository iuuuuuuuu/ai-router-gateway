# Agent Note: 页面显式保存直接持久化配置

Status: implemented

## Problem

渠道与模型弹窗、分组设置和模型配置的保存操作原先只修改共享内存，仍需点击顶栏保存。用户容易把弹窗关闭和成功提示理解为已经落库。分组列表读取旧的 exposed_models，可能出现已有成员但暴露模型为零；分组详情的密钥区域也缺少配置入口。

## Decision

共享 store 提供 persistConfigChange，在独立配置副本上应用操作、校验引用并提交配置。提交成功才发布到共享状态；失败保留原配置和表单，允许重试，避免失败后重复插入。保存期间阻止重复提交和相关弹窗关闭。

渠道保存、手动模型保存、获取模型后的批量导入、分组创建、分组设置和层级保存使用该入口。分组详情提供密钥添加、启停和删除入口，操作直接持久化；列表仍只展示脱敏密钥。

提交副本按层级顺序及成员声明顺序汇总暴露模型并首次去重，与服务端规则一致，不按启用状态或权重过滤。请求期间若共享配置发生变化，保留新编辑并维持 dirty 状态，不把新编辑误标为已保存。

## Alternatives considered

- 保留顶栏统一保存：改动最小，适合集中提交多处草稿；但页面明确的保存按钮仍不代表持久化，延续本次交互问题，因此不采用。
- 先修改共享配置再提交：可复用旧代码；但请求失败后新增项已经存在，重试容易触发重复校验，回滚还可能覆盖其他编辑，因此采用候选副本。

## Consequences

- 收益：显式保存与实际落库一致，失败可保留输入重试，保存后暴露模型显示与成员配置同步，分组密钥可直接管理。
- 代价：后端仍是整份配置提交，因此页面保存也会提交共享配置中已有的未保存修改；并发编辑仍需保留 dirty 状态并再次保存，不提供字段级事务。
- 范围：未将所有删除或行内编辑统一改为自动保存，也未修改服务端配置接口。

## Verification

- 前端及桌面构建已通过；构建不替代功能验收。
- 真实桌面客户端已验证渠道、手动模型保存失败保留输入，恢复连接后重试各只持久化一次。
- 已通过真实界面验证分组创建、设置保存、密钥添加和启停，以及成员保存后的暴露模型显示；通过管理接口回读确认落库。
- 刷新客户端后再次确认渠道、模型、分组设置、成员、暴露模型和密钥仍保留。
- 验收数据已移除，管理接口回读结果与验收前完整配置一致。
- 批量导入：真实 `models` 接口拉取后勾选两项，故障注入下保存失败仍保留 2 项勾选，恢复后重试两模型各唯一落库。
- 密钥删除：故障注入删除失败时界面与服务端均保留该密钥，恢复后重试删除成功且界面同步消失。
- 保存期间并发编辑：包装真实 `fetch` 只延迟 `PUT /admin/api/config` 的响应（不伪造响应），在窗口内切换渠道开关；保存返回后该编辑未被覆盖、顶栏仍标记「有未保存的修改」，再次保存后落库。
