# 开发入口（AGENTS）

> 面向在这个仓库里动手的人（含 AI agent）。**开工前读完本页。**
> 最后核对：2026-10-15。**已发布最新版 = v0.4.6**；HEAD（`0dd8cfa`）上还带着**未发版的 v0.4.7** 改动。
> 改命令、约束、流程时同步更新本页。

## 0. 一句话

多渠道多模型 AI 网关：**分组多级容灾路由 + 三协议互转 + 成本统计 + 完整日志**。

核心承诺：**「模型失败 = 网关的内部事务，客户端永远无感」** —— 只有两种互斥结局：**成功**（完整内容 + 完整 usage）或**失败**（一个结构合法的标准错误）。**中间态即 bug。**

## 1. 仓库结构

| 目录 | 是什么 | 产出 |
|---|---|---|
| `server/` | Rust 网关（axum 0.8 + reqwest 0.13 + rusqlite 0.40），数据面 + 管理面 | 单文件 `server/target/release/gw-server.exe`（约 5MB） |
| `client/` | Tauri 2 + Vue 3 桌面控制台，托管网关进程（sidecar）、托盘、开机自启（默认关） | `client/dist/` + NSIS 安装包 |
| `client/src-tauri/` | Tauri 壳：sidecar 拉起、托盘、窗口状态 | `binaries/gw-server-x86_64-pc-windows-msvc.exe`（**入库**） |
| `docs/` | 设计与规格文档 | 见 [README.md](README.md) 文档地图 |
| `tools/` | 开发期探针与构建脚本（**绝大多数不入库**，见 §5.3） | 真机验收证据 |

服务端模块地图：`config.rs`（配置与默认值）· `router.rs`（候选/层级/循环）· `proxy.rs`（尝试与提交点状态机）· `protocol/`（三协议互转 + IR）· `health.rs`（冷却归因）· `store.rs`（SQLite：配置/日志/统计）· `admin.rs` + `routes.rs`（HTTP 面）· `loopguard.rs`（退化输出判定）· `inflight.rs`（实时并发）· `tls.rs`（自签证书）。

## 2. 环境与命令

本机工具链实测（2026-10-15）：`rustc 1.99.0` / `cargo 1.99.0` / `node v25.9.0` / `pnpm 11.7.0` / `gh 2.102.0`。

| 用途 | 命令 |
|---|---|
| 服务端构建 | `cd server && cargo build --release` |
| **服务端测试（主门禁）** | `cd server && cargo test --release` |
| 前端构建 | `cd client && pnpm build` |
| 客户端开发（热更新） | `cd client && pnpm tauri dev` |
| 客户端完整构建（安装包） | `cd client && pnpm tauri build` |
| 本机跑起客户端（带 CDP 调试口） | `node tools/start-client.mjs <release 目录> 9223` |

### 2.1 ★ `node_modules/.bin` shim 陷阱（真实踩过）

本机 bash **没有 coreutils**（无 sed / dirname / uname / tail），而 `node_modules/.bin/*` 的 shim 需要它们。历史上因此拿到过两种**假象**：一次是**假的 exit 0**（末尾 echo 成功、构建其实没跑），一次是 MODULE_NOT_FOUND —— 两次看起来都像产品缺陷，实际是工具链问题。

**脚本化构建要直接调 JS 入口**：

```bash
node node_modules/vite/bin/vite.js build
node node_modules/@tauri-apps/cli/tauri.js build
```

（本机另有一份 `tools/_build-client.sh` 封装了同样两条命令，但它**不入库**，见 §5.3 —— 新克隆的仓库里没有它，按上面两条命令自己写即可。）

### 2.3 数据与配置

- 配置持久化在 SQLite；`GW_DATA_DIR` 指定目录（自动接 `gateway.db`）或直接指定 db 文件路径；不设则用**可执行文件同级目录**。
- 首次启动用默认配置，之后通过管理面 `PUT /admin/api/config`（或客户端 UI）修改并**热更新**（`config_version` 递增）。**例外：监听地址改动需重启。**
- 开发期（debug 构建）客户端把数据放 `client/src-tauri/target/<profile>/data`；release 放 exe 同级。

## 3. 硬约束（不许破坏）

### 3.1 五条不变量（I1–I5）

| # | 不变量 | 断言方式 |
|---|---|---|
| I1 | 提交点之前，**客户端 socket 字节数恒为 0** | 字节级记录 |
| I2 | 终态二选一且互斥（不存在半成品） | 状态机断言 |
| I3 | 单请求内同一 (channel, model) 最多尝试一次 | 候选集快照 |
| I4 | `max_attempts × attempt_deadline_ms + reserve_ms ≤ total_deadline_ms` | 加载期 + `PUT` 校验，违规 400 且零字节落库 |
| I5 | 全冷却必须**等待**，禁止零次 attempt 直接失败 | 状态机断言 |

I4 的默认值刚好合法，**改任何一个默认值都要重算**：`6 × 25000 + 3000 = 153000 ≤ 180000`。

loop guard 另加一条 **I6**：提交后命中退化时，客户端已收到的字节**绝不撤回、绝不重发**，只就地截断 + 正常收尾，且**截断必须落库可见**（`loop_truncated`），不得伪装成完好回答。详见 [loopguard-spec.md](loopguard-spec.md)。

### 3.2 诚实边界（★ 不许说得比实际好）

这些是**物理限制或刻意取舍**，不是待修的缺陷。改代码或写文档时都不许把它们说没：

| 边界 | 内容 |
|---|---|
| 提交后一定泄漏一小段 | 已经发给客户端的字节收不回来。提交后命中退化**必然**泄漏一段复读文本，泄漏量受 `loop_guard_tail_chars`（默认 128）与纠正轮数共同约束，不等式钉在测试 `l13f`：`leaked <= (1 + loop_continues) * repeat_min_chars` |
| 提交后单元长度窗口 | 默认阈值下，提交后**只能**拦下约 24–25 字符的重复单元；22/23 与 26 以上的单元在提交后整段泄漏（提交前仍能拦）。硬边界，见 [loopguard-spec.md](loopguard-spec.md) §8 |
| 只有流式路径检测 | `stream: false` 一次拿完整 JSON，没有增量帧，**不检测**退化 |
| loop guard 代价 | 开启后首字节推迟约 `loop_guard_min_chars`（默认 64）个字符；关掉立即返回但不再拦截 |
| 思考透传：Anthropic 缓冲路径丢思考块 | Anthropic 校验思考块的 `signature`，网关不携带签名，回放无签名块会把下一轮请求变成 400，所以**缓冲响应里丢弃**；流式照常透传 |
| 思考透传：OpenAI 缓冲路径丢思考 | 不发明客户端没要的 `reasoning_content` 字段。要拿思考就用流式 |
| 密钥**未加密** | 密钥只是从 `config_json` **搬到了 `secrets` 表**（存储分离），库里仍是明文；拿到 `gateway.db` 就能读。DPAPI/OS 级加密**仍未做** |
| 上游对账不完整 | `wasted_cost_usd` 只在**本地观测到 usage** 时计价；上游已计费但我们没解析到 usage 的尝试仍记 0 —— 这是「没有证据就不编数」 |

### 3.3 其它必须记住的语义

- **暴露模型是派生值**：服务端按分组成员**自动维护** `exposed_models`，不再手填；进程启动时会重新派生并落库（`normalize_exposed_models`），所以「新进程读到的列表」与「运行中网关真正认的列表」不会不一致。
- **分组名即模型名**：分组的名称与 id 本身可直接作为 `model` 调用；但**精确名优先** —— 请求的模型名若命中某分组的 `exposed_models`，走窄语义，不被同名分组截走。
- **报错文案**：面向调用方的 `message` **一律中文**；`code` 标识符保持英文供程序判断。失败词表**只有一份**（`store::error_class_label`），控制台 / 切换日志 / 客户端消息共用。
- **时长**：界面一律显示中文「秒」（`0.03秒` / `4分30秒`）；**接口契约仍是毫秒**（`retry.*_ms` / `duration_ms` / `ttft_ms`），输入框按秒填、内部按毫秒存。
- **TPS 口径**：`输出 tokens ÷ 解码耗时`，解码耗时 = 总耗时 − 首字耗时；**解码窗口不足 200ms 时退化为按总耗时算**（宁可偏低也不虚高）。
- **提交点**：流式请求收到**第一个合法内容帧**后才向客户端写首字节；失败切换对客户端完全透明。
- **中途断流**：网关补 repair 帧（`gateway_upstream_interrupted`）+ 正常终止符，客户端永远拿到结构完整的响应。

## 4. 工作流

1. **先读文档**：本页 → 与改动相关的主题文档（[文档地图](README.md)）。
2. **改代码**：改动范围只落在被指派的部分；连带影响可自主修掉，不相关的**不碰**。
3. **写/改测试**：新能力必须有能**真的变红**的门禁（见 §5.1）。改判定阈值 → 同步钉住该数字的测试。
4. **同步文档**：行为变化 → [FEATURES.md](FEATURES.md)；决策变化 → [DECISIONS.md](DECISIONS.md)；流程变化 → [RUNBOOK.md](RUNBOOK.md)。
5. **提交**：见 §5.3（显式列路径，禁 `git add -A`）。
6. **发版**：见 [RUNBOOK.md](RUNBOOK.md)。

## 5. 交付与验证纪律

### 5.1 ★ 禁止假绿门禁

**任何测试/校验/CI 都不得「显示通过但实际没验证到东西」。** 具体形态：断言被跳过或吞异常、mock/桩替掉真实逻辑、脚本恒 `exit 0`、只跑编译或单测就宣称通过、失败用例被注释或降级、占位 always-pass、靠 `|| true` 或忽略退出码蒙过。

**门禁必须驱动真实路径**（实机 / 真请求 / 真数据），且**必须能真的变红**：新门禁先做**故障注入**证明它会失败，才承认它是绿的。

发现假绿按**缺陷**处理：先修门禁，再谈交付。

### 5.2 实测纪律

- **攒批**：改动攒完、任务全做完后**最后统一实测一次**（一次构建 + 部署 + 实机验证），不要每改一处验一次。
- **「完整跑实测」= 本轮 diff 影响到的功能逐条真跑**，不是全 app 全量回归，也**不是**只跑编译/单测。**编译过 / 单测绿 / SHA256 对得上都不算实测。**
- 只约束**验证**时机：commit 可按项做（便宜），构建 + 部署 + 实机验证攒到批末（贵）。
- **完全无干扰**：使用者可能正在用同一台电脑 —— 绝不动鼠标、不抢焦点、不点桌面，也不要让使用者代点。用探针完成（见 [TESTING.md](TESTING.md)）。
- **有在途未提交改动时，「在某个提交上跑测试」实际测的是工作树。** 要证明「修复前应当红」的红基线，必须用 `git worktree add` 检出纯净副本再跑。

### 5.3 Git 与隐私

- **禁止 `git add -A`**，必须**显式列路径**。
- **提交前清理敏感信息**，确认干净才允许 commit。
- 隐私检查要扫**整棵已发布树**，不能只扫这次的暂存 diff —— 扫 diff 只证明这次干净，证明不了上次没带进去。做法：`git grep -n -E '<本机标识>' HEAD -- .`，推送后再对远端 HEAD 确认一次。
- **本仓库没有 `check:privacy` 之类的专用隐私门禁工具**（`client/package.json` 只有 `dev` / `build` / `tauri`），**不要去跑不存在的命令**，按上面的 `git grep` 自查即可。
- 易漏的未跟踪项先进 `.gitignore` 而不是提交：本机探针与截图、本机构建脚本、发布暂存目录、`*.db`、日志、真实配置。
- ★ **探针是逐条登记的，不是通配忽略**：`.gitignore` 里没有 `tools/_accept-*` 这样的 glob，每条探针（`tools/_accept-gdpage.mjs`、`tools/_diag-r4.mjs` …）各自一行。所以**新写一个探针，它默认是「未跟踪」状态，必须手动往 `.gitignore` 加一行**，否则会被 `git add` 带进仓库（并可能带进本机端点/密钥）。加完用 `git status --porcelain` 确认它不再出现在未跟踪列表里。
- **本地 commit 不限量**；推远端 / 开 PR 需明确授权，且 PR 前必须先过完整实机测试 + 逐行自审。

### 5.4 删除纪律

**小心 / 不误删 / 不扩大范围。** 只删点名的那一个对象；删前确认**解析后的绝对路径**（防 junction / 符号链接穿透）；批量清理的匹配条件**必须锚定本仓库路径**，绝不用通用文件名（如 `node.exe` / `vite.js`）作唯一条件；**先列清单再执行**，不得「先杀后核」。

## 6. 不要做的事

- 不要为了「看起来更完整」而补文档章节 —— 只写读不出来的。
- 不要把诚实边界写成「已解决」或删掉。
- 不要在没有故障注入证明的情况下宣称新门禁有效。
- 不要用 `node_modules/.bin` 的 shim 跑批量构建（§2.1）。
- 不要把本机绝对路径、真实密钥、探针产物写进仓库文件。
- 不要在没有授权时推远端或开 PR。
