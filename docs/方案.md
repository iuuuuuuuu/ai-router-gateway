# AI 模型路由网关 · 方案 v0.4

> v0.4 变更:技术栈改为 **Rust**;连通性测试改为**真实请求**(不封号);协议范围定为 **OpenAI / Anthropic Claude / Google Gemini 三格式互转**;部署支持 **HTTP + HTTPS**。
> 依据:同口径实测(本机 Windows x64 / rustc 1.99.0 / Node v26.0.0)。

---

## 0. 核心原则:失败只在网关内部消化

**"模型失败 = 网关的内部事务",客户端永远无感。**

只有两种结局且互斥:**成功**(完整内容+完整 usage)或**失败**(一个结构合法的标准错误)。中间态即 bug。

### 0.1 五条不变量(CI 断言)

| # | 不变量 | 断言方式 |
|---|---|---|
| I1 | 提交点之前,**客户端 socket 字节数恒为 0** | 字节级记录 |
| I2 | 终态二选一且互斥 | 状态机断言 |
| I3 | 单请求内同一 (channel, model) 最多尝试一次 | 候选集快照 |
| I4 | `max_attempts × attempt_deadline + reserve ≤ total_deadline` | 加载期校验 |
| I5 | 全冷却必须走等待,禁止零次 attempt 直接失败 | 状态机断言 |

### 0.2 提交点之前对客户端零字节

v0.2 曾写「重试期间发 `: keep-alive`」—— **实测证明它摧毁核心承诺**:一旦写出首字节,HTTP 头落地,网关**永久失去返回 502 的能力**。

**裁决:提交点前对客户端零字节;保活走 TCP 层**(不产生应用层字节)。

### 0.3 本地可验证的终极判据

> **拿一条完整的客户端 SSE 字节流,用正则扫描是否出现任何上游错误文案 / 上游 key / 上游错误码。命中即失败。**
> 这条断言进 CI,是"失败永不外漏"唯一可证伪的形式。

## 1. 技术选型:为什么是 Rust(同口径实测,非推演)

你的要求是**轻量、占用小、速度快**。我实测了一个「完整网关骨架」(axum + reqwest + SQLite + SSE)与 Node 基线:

| 指标 | **Rust(axum+reqwest+rusqlite)** | Node(裸 http 基线) | 结论 |
|---|---|---|---|
| **可执行文件体积** | **3.05 MB** | 93.42 MB(node.exe 本体) | **31× 小** |
| **常驻内存 RSS** | **6.19 MB** | 63.62 MB | **10× 小** |
| **冷启动** | **343 ms** | 405 ms | 更快 |
| 依赖外部运行时 | 无(单文件) | 需装 Node | ✅ 真正零安装 |

> 说明:Node 基线是**裸 http server**(未装任何依赖),真实 Fastify+SQLite 组合只会更大(实测 node_modules 另需 45–60 MB)。Rust 数字来自本机 Release 构建(opt-level="z" + LTO + strip)。

**关键:这正好一次性解决了 v0.3 遗留的最大遗憾** —— v0.3 用 Node 时,"客户端 ~10MB + 服务端 ~120MB"的体积承诺是假的;换 Rust 后**服务端本身就是 3MB 单文件**,不再需要取舍。

### 1.1 版本锁定(本机 crates.io 实查)

| 依赖 | 版本 | 关键点(实查 feature) |
|---|---|---|
| axum | **0.8.9** | 路由;流式需 `Body::from_stream` + `reply.hijack()` |
| tokio | **1.53.2** | full features |
| reqwest | **0.13.5** | **默认 TLS 就是 rustls**(feature `default-tls = ["rustls"]`)**无需 OpenSSL DLL**;流式用 `stream` + `bytes_stream()` |
| rusqlite | **0.40.2** | `bundled` 内联 SQLite,静态链接,无额外 DLL |
| tower-http | 0.7.1 | trace / 限流 / CORS |
| windows-service | 0.8.1 | Windows 服务注册(开机自启) |
| eventsource-stream | 0.2.3 | 标准 SSE 帧解析(**跨 chunk 帧**,不能自己 split) |

> reqwest 0.13 默认走 rustls 这一条很重要:意味着**单文件 exe 不带 OpenSSL**,目标机无需装 VC++ Runtime。

## 2. 协议支持:三格式互转(你的要求 1)

**客户端用三种格式中的任意一种调用网关,网关按渠道协议互转。**

### 2.1 两种方向

| 方向 | 说明 |
|---|---|
| **入口侧** | 客户端用 OpenAI / Anthropic / Gemini 任一格式调用 → 网关归一化为内部表示 |
| **出口侧** | 渠道是任一格式 → 网关按客户端格式渲染响应(含流式) |

**入口路由**:
- `/v1/chat/completions`(OpenAI)
- `/v1/messages`(Anthropic)
- `/v1beta/models/{model}:generateContent` + `:streamGenerateContent?alt=sse`(Gemini)

### 2.2 内部统一表示(IR)

请求归一化为:
```
messages: [{role, content: [Text|Image|ToolUse|ToolResult]}]
system:   [Text]
max_tokens, temperature, top_p, stop_sequences, stream,
tools:    [{name, description, input_schema}],
tool_choice
```
响应渲染为:
```
finish_reason 映射: stop→stop/stop_sequence | length→max_tokens | tool_use→tool_calls
usage:         input_tokens / output_tokens / cache_read / cache_creation
```

### 2.3 三家差异(实现要点,这是最容易出错的地方)

| 维度 | OpenAI | Anthropic | Gemini |
|---|---|---|---|
| max_tokens | 可选 | **必填** | 可选 |
| system | 消息内 role=system | **顶层字段** | 顶层 `systemInstruction` |
| 鉴权头 | `Authorization: Bearer` | `x-api-key` + `anthropic-version: 2023-06-01` | `x-goog-api-key` |
| 流式终止 | `data: [DONE]` | `message_stop` 事件 | 无 DONE,靠 JSON 数组结束 |
| usage 字段 | `prompt_tokens/completion_tokens` | `input_tokens/output_tokens` | `usageMetadata` |
| 缓存 | — | `cache_creation_input_tokens` / `cache_read_input_tokens` | `cachedContentTokenCount` |

**最易踩的坑**:
- OpenAI `tool_calls` 的 `delta` 是**分片**的(id/arguments 分散在多个 chunk),必须累积后再合并;
- Anthropic 的 `input_json_delta` 同样是**部分 JSON 字符串**,需拼接;
- Gemini 的 `functionCall.args` 也可能分块;
- **流式语义不同**:OpenAI 是纯增量;Anthropic 有 `content_block_start/delta/stop` 三段式;Gemini 是完整累计对象。转换时必须知道"下游想要增量"。

## 3. 连通性测试:必须真实请求(你的要求,避免封号)

**你说得对——探测不能只用 `GET /v1/models` 或空请求,容易被风控判定为异常流量封号。**

### 3.1 规则

| 场景 | 行为 |
|---|---|
| 渠道「测试连通」 | **发送一次真实最小对话请求**(如 `max_tokens=1`,内容 "hi"),走完整鉴权+路由链路 |
| 请求内容 | 从**该渠道真实历史请求**里取样(脱敏后),或用内置安全短语;**绝不构造探测特征明显的垃圾请求** |
| 频率 | **默认关闭自动探测**,仅手动触发;可配置最短间隔(默认 ≥10 分钟)防刷 |
| 判定 | 只看「是否拿到合法响应帧」,**不因内容质量判定失败** |
| 401/403 | 判定为**密钥问题**(不是网络问题),提示重配,**不重试、不冷却其他渠道** |

### 3.2 健康检查的重新定位(重要)

**删除 v0.2/v0.3 的"后台定时主动健康检查"设计**(会误杀低频健康渠道 + 自身触发风控)。

健康状态**只由被动信号驱动**(真实业务请求的成功/失败):
- 失败 → 按错误类型归因冷却(见 §5);
- 成功 → 出冷却;
- 渠道管理页提供**手动"测试连通"按钮**(真实请求,可随时点)。

## 4. 路由引擎(Rust 实现要点)

保留 v0.3 的状态机(v0.3 已补齐 WAIT_FOR_COOLDOWN / 候选快照 / 预算预留),Rust 侧落地要点:

- **冷却与轮询用 `dashmap`** 或 `Arc<Mutex<...>>`;轮询用**平滑加权轮询 SWRR**(无游标,天然抗并发增删);
- **超时用 `tokio::time::timeout` 分层包裹**,配合 `CancellationToken` 做取消传播;
- **SSE 用 `eventsource-stream`** 解析,禁止自己 split;
- **取消传播**:客户端断开 → 取消上游 future(防止白烧钱);
- **背压**:`Body::from_stream` 天然流式,不做全量缓冲。

## 5. 健康归因(保留 v0.3 修正)

| 键 | 归因 | 冷却 |
|---|---|---|
| channel | 401/403 | 永久 + 需重配 |
| channel+model | 404 model_not_found | 长期排除 + 持久化 |
| channel+model | 429 | max(Retry-After, 退避) |
| channel+model | 5xx/超时/连接错 | 指数退避(有上限) |

**退避修正**:失败只在**连续失败≥阈值**时推进,收到成功才重置(v0.2「成功立即出冷却 + 指数退避」在 429 下永久熔断)。

## 6. 成本核算(双维度)

每 attempt 独立记账:`external_model`(对外名) / `upstream_model`(实际上游) / channel / tier / group / key。

- `billed_cost`(用户可见)= 仅已提交 attempt;
- `upstream_billed_cost`(对账)= 全部 attempt(失败也可能扣上游);
- **价格快照**;四类 token(input/output/cached_read/cache_creation);
- 缺 usage → `estimated` 标记,不参与对账;
- **成本浪费榜**:按渠道统计提交前失败的浪费 —— 发现坏渠道的最强信号。

### v0.3.0 / v0.4.0 新增能力（实现依据）

**1. 死循环输出拦截（loop guard，v0.3.0）**

模型陷入重复输出时，网关在**内部**把它判为一次可重试的上游失败：丢弃该次尝试、按路由规则换下一个候选，客户端只看到一次正常回答、提交前零字节（I1 不变）。

- 实现：`server/src/loopguard.rs`（模块文档 + `LoopCfg` + `from_retry` 钳位 + `detect`），判定在 `server/src/proxy.rs` 的 pre-commit 缓冲窗口内做，命中写 `error_class = "degenerate_output"`。
- 判定语义（滚动字符窗口上的 5 条规则，注释在 `server/src/loopguard.rs` 的 `detect()` 里逐条标为 R1–R5）：R1 缓冲长度 `n ≥ min_chars`；R2 重复次数 `repeats ≥ max_repeats`；R3 重复覆盖字符数 `covered ≥ repeat_min_chars`；R4 重复占比 `covered ≥ repeat_ratio × n`；R5 重复单元不能整个落在窗口尾部的空白串里。多解取覆盖最多者，并列取单元最短。
- 完整规格（含钳位范围、`LoopHit`、holdback 语义、15 条必须覆盖的测试）：`docs/loopguard-spec.md`。
- 观测：`switch_logs` 每条退化尝试单独一行（`outcome = "failed"`、`error_class = "degenerate_output"`），`request_logs` / `stats_*` / `group_member_stats` 都带出 `loop_retries`；客户端日志页显示为「输出退化」（warn 色），统计页与分组/模型详情展示 `loop_retries`。
- 诚实边界（与 README 同一口径）：**只覆盖流式路径**（`stream: false` 没有增量帧，不检测）；**只有提交前能内部重试**（已向客户端写出首字节后再退化无法换候选，沿用 `feed_repair` 补错误帧 + 正常终止符，带 `finish_reason=error`）；开启后**首字节推迟约 `min_chars` 个字符（默认 64，可配）**；误判可能（长文里恰好高比例重复），命中只影响该次尝试。

**2. 分组名即模型名（通配路由，v0.3.0）**

每个分组的 `name` 和 `id` 本身就是可直接调用的模型名：请求 `model: "<分组名>"` 时该组所有层级的启用成员都是候选池。

- 实现：`server/src/router.rs` 的 `is_wildcard(group, requested)`（`server/src/router.rs:111`）——请求名命中该组 `exposed_models` 时返回 `false`（**EXACT WINS**，窄语义字节不变），否则 `requested == group.name || requested == group.id`；`build_plan` 与 404 守卫都走这一个判定。
- 发现：`GET /v1/models`（`server/src/routes.rs` 的 `list_models`）先列 `exposed_models`，再补该组 `name` 与 `id` 并去重。
- 客户端「分组路由」页每个分组都有一键复制模型名的提示。

**3. 每个分组可跟随全局配置，也可有自己的配置（v0.3.0）**

- 数据模型：`server/src/config.rs` 的 `GroupOverrides { #[serde(default)] pub retry: Option<RetryConfig> }`（`retry` 故意不 `skip_serializing`：`None` 必须序列化成 `"retry": null`，这是控制台区分「跟随」与「自有」的唯一判据）。
- 取值：`effective_retry(cfg, group)`（`server/src/config.rs:276`）= `group.overrides.retry.as_ref().unwrap_or(&cfg.retry)`，数据面与 `group-members` 端点共用同一个函数。
- 回报：`GET /admin/api/group-members` 返回 `retry`（生效值）、`retry_source`（`"group"` / `"global"`，`server/src/admin.rs:544`）与 `global_retry`（全局那份，供界面显示「跟随全局（当前：…）」）。
- 校验：组级预算同样受 I4 约束（`max_attempts × attempt_deadline_ms + reserve_ms ≤ total_deadline_ms`），不合法时 `PUT /admin/api/config` 返回 400（`group {id}: {msg}`）且不写入。
- 缺键语义：手写配置里缺 `loop_guard_*` 时服务端按 **serde 默认值**（`server/src/config.rs` 的 `#[serde(default = "d_*")]`）而非全局值生效。

**4. 添加模型：手动填写，或从上游 models 接口拉取（v0.4.0）**

- 服务端：`POST /admin/api/channel-models`（`server/src/admin.rs` 的 `channel_models`）——调用方给已保存的 `channel_id`，或直接给草稿 `base_url` / `api_key` / `protocol` / `headers`（草稿字段优先，请求头按同名 MERGE，与数据面同规则）。
- 语义：**答案永远是 HTTP 200**，能不能连通是业务事实报在 `ok`；`status` 是上游 HTTP 状态（0 = 没连上）；`models` 是去重后的 id 列表，另有 `count` / `latency_ms` / `truncated`。
- 超时与上限：整段请求（**含响应体**）共用一个 20 秒超时，上游先回响应头再挂住 body 也不会让弹窗一直转圈；模型数上限 5000（超出截断并置 `truncated`）。
- 「空列表」与「不可识别载荷」按 payload 形状区分：体是模型列表但一条都没有 → 合法空答案；体根本不是模型列表（HTML / `{}` / 裸字符串 / 空体）→ 报错，不假装成「这个渠道没有模型」。
- 客户端：「渠道与模型」页工具条与每张渠道卡片都有入口，弹窗内两种并列方式（手动填写 / 从 models 接口获取）；已在本渠道绑定过的上游模型显示「已存在」且不可勾选；失败在弹窗状态区可见地报出（如 `HTTP 401`）。

### 工具调用参数保真（2026-10 修复）

**症状**：流式工具调用到达客户端时 `args` / `arguments` / `input` 变成空对象——不是报错，是**静默数据损坏**（客户端以为模型调用了一个无参数的工具）。

**根因（三处输出侧丢参数）**：

1. `protocol/gemini.rs` 的 `render_stream_event` 把 `ToolUseStart` 硬编码渲染成 `"args": {}`，并把 `ToolInputDelta` 渲染成空 vec —— 参数全部丢弃。
2. `proxy.rs` pre-commit 的 `FrameClass::ToolCallFull`（Gemini 整包 functionCall）只取 `name`，`args` 被解构后未使用。
3. 上游分类器把「name 与 arguments 同帧」的厂商（部分 OpenAI 兼容、Anthropic `content_block_start` 已带完整 input）的同帧参数丢掉。

**修复**：

- `StreamEvent::ToolUseStart` 增加 `args: Option<Value>`：`Some` = 上游整包下发（Gemini 原生形状），`None` = 参数随后以 `ToolInputDelta` 分片到达。渲染器**不得**为 `None` 编造空对象。
- Gemini 渲染器：`Some` 直接渲染完整 `functionCall`；`None` 渲染空 vec（由 proxy 装配后再发）。OpenAI 渲染器把 `Some` 序列化成 `arguments` 字符串；Anthropic 渲染器额外补一条 `input_json_delta`。
- proxy 新增 `pending_tool` 累积器 + `flush_tool()`：分片参数累积到 **Finish 之前**才合成**唯一**一个整包 `ToolUseStart`（Gemini 的 functionCall 是整包语义，分片渲染会让客户端看到两次调用）。提交路径（commit 事件本身即工具调用）走同一套装配。
- 上游分类器保留同帧参数（`Classified::ToolUseStart` 增加 `args` 字段）。

**回归**：新增 fixture `GoodGeminiToolStream` / `GoodOpenAiToolStream` / `GoodOpenAiToolOneFrame` / `GoodAnthropicToolStream` 与测试 p11–p14；mock 上游加 `#TOOL` 探针（三协议都返回带真实参数的调用）。实测三入口 × 流式/非流式参数全部保真，日志与成本记录正常。
