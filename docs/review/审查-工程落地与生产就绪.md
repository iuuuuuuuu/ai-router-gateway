## 0. 先说结论（实测出来的硬事实）

我按方案 §2.2 实现了一版缓冲-提交代理 + 11 种假上游 + 3 档提交点，跑通 **33 组矩阵**（11 模式 × 3 提交点 × 10 降级场景）。核心承诺**是可实现的**，但方案本身有一处自相矛盾、一处隐性陷阱、三个「实现即踩」的坑。

**结论 1 —— 核心承诺成立，但仅限「提交点之前」。**

10 个降级场景（连接拒绝 / 500 / 200+error / 非法 SSE / 空 body / 卡死 / 429 → 最终落到 ok 渠道）在 a/b/c 三档提交点下，客户端一律拿到 `200 text/event-stream` + 完整 `[DONE]` + `finish_reason`，重组文本 `tok1tok2tok3` 一次不缺，上游错误文案零泄漏。**方案 §0 的主张是真的。**

**结论 2 —— §2.2 的「重试期间发送 `: keep-alive` 注释行」直接摧毁 §0.2 的「干净 502」承诺。**

实测复现（见 §1.1）：keep-alive 一开，HTTP 响应头立即落到线路上，`headersSent=true`，网关**再也无法发出 502**。客户端实测拿到 `200` + `content-type: null` + 半截 SSE。**这是方案文档内部打架，必须先书面裁决。**

**结论 3 —— 提交点 b/c 对「中途断流」无效，且比 a 更危险。**

实测（见 §1.2）：a/b 下中途断流会让客户端拿到「**有 `[DONE]` 但没有 `finish_reason`**」的流 —— 看起来完全成功，实际已被截断。而 c 因为全程缓冲、能识别无 `[DONE]`，反而干净地返回了 502。**「只发 `[DONE]`」是 bug。**

另外三个实测坑（影响技术选型，见 §1.4）：`node:sqlite` 在 BIGINT 超 2^53 时**直接抛异常**；WAL 下第二个写连接**立刻 `SQLITE_BUSY`**；`node:sqlite` **没有 `db.backup()`**。

## 1. 技术选型风险

### 1.1 【最高危】方案自相矛盾：提交前发 keep-alive = 永久放弃干净 502

方案 §2.2 写：「重试期间对 SSE 连接发送 `: keep-alive` 注释行」。**这一行字会让 HTTP 响应头立即落到线路上**，`res.headersSent` 变成 `true`，从此网关**再也无法发送 502**。

实测（同一份代码，只切换 keep-alive 开关，3 次失败 attempt、每次 800ms、心跳 300ms）：

| keep-alive | 客户端实际拿到 | 契约判定 |
|---|---|---|
| 关 | `502` `application/json` `{"error":{"type":"gateway_exhausted"}}` | ✅ 契约成立 |
| 开 | `200`，`content-type` 为 `null`，body = `: keep-alive\n\ndata: {"error":...` | ❌ **契约破裂** |

注意第二行的 `content-type: null` —— Node 先隐式写出 `200` 默认头，Fastify 再也改不了。客户端 SDK 会拿到「200 + 半截 SSE」，按 status 做重试的逻辑全部失效。

**这不是实现细节，是方案必须二选一的设计决策：**

- **选 A（推荐）**：**提交点之前对客户端零字节**，删掉 keep-alive 注释行能力。
  - 代价：上游全死时，网关要等预算耗尽才第一次写响应头。若 `total_deadline=120s`，客户端可能先超时。
  - 对策：把「预提交窗口」压到客户端超时之内 —— 网关在 ~3s 内必须给出第一次响应（成功则提交，失败则 502 或 error frame）。即 `total_deadline` 必须显著小于客户端超时。
  - 保活改用 **TCP 层**（`TCP_KEEPIDLE` / `TCP_KEEPINTVL`）而不是应用层字节 —— 这对客户端和中间代理都不可见。

- **选 B**：保留 keep-alive，但**接受契约变更** ——「提交前失败」不再是 502 JSON，而是 `200 + data:{"error"}`。那就必须改掉 §0.2/§2.3 的文案，并显式声明「100% 无感」只覆盖语义合法，不覆盖状态码。

> 与 [审查-事故复盘.md P0-01/P0-02](审查-事故复盘.md) 指向同一问题，我的实测提供了第一手复现数据。

### 1.2 提交点 b/c 对「中途断流」无效，且比 a 更危险

实测 `midway_disconnect`（发了 2 个 delta 后 socket 被 destroy）：

| 提交点 | 客户端拿到 | 重建内容 | 有 `[DONE]` | 有 `finish_reason` |
|---|---|---|---|---|
| a | `200` | `Hello world` | ✅ | ❌ |
| b | `200` | `Hello world` | ✅ | ❌ |
| **c** | **`502`** | — | — | — |

- a / b：客户端拿到 **`[DONE]` 但没有 `finish_reason`** 的流。这是最危险的一种 —— **看起来完全成功**。多数 SDK 不校验 `finish_reason`，用户会以为拿到了完整答案，实际被截断了。
- c：反而因为全程缓冲、能识别「无 `[DONE]`」而干净地返回 502。

**推论（直接写进实现规范）：**
1. **提交后的收尾必须补 `finish_reason`**，不能只发 `[DONE]`。要么补 `finish_reason: "stop"`（§2.4 策略 1「优雅收尾」），要么发 `finish_reason: "error"` + error 帧（策略 2）。
2. 默认提交点建议 **a**；b/c 仅对「已知脏上游」的渠道开白名单。原因：重试期间本来就不写客户端，b/c 挡「脏上游」的核心收益已在预提交窗口拿到；而它的代价是首字延迟 + 半开连接窗口。
3. 文档要告诉用户：客户端侧应加断言 —— 收到流但无 `finish_reason` 且无 `[DONE]` 即视为截断。

### 1.3 Node + Fastify 做流式网关的真实风险

| 风险 | 具体表现 | 对策 |
|---|---|---|
| **Fastify 会破坏流** | `reply.send(obj)` 默认 JSON 序列化，走这条路径后再手写 `res.write` 会乱 | 流式路由**禁用 schema 序列化**，用 `reply.raw` 直写，`Content-Type` 手工设 |
| **Nagle 延迟首字节** | `res.write` 默认开 Nagle，TTFB 多约 40ms | `res.socket.setNoDelay(true)`（我的原型实测加上才正常） |
| **背压缺失 → 内存无界** | 客户端慢读时继续读上游，内存涨到 OOM | `res.write()` 返回 `false` 时**必须 `pause()` 上游 reader**，等 `drain` 再 `resume()` |
| **半开连接击穿** | 上游不发 FIN 也不断，chunk 间隔超时无人管 | 上游侧必须有 **chunk idle timer**（原型 500ms，实测能兜住 `stall_midway`） |
| **AbortController 泄漏** | 每次 attempt 新建 controller，异常路径忘 `clearTimeout` | 统一 helper 管理；测试断言「所有 timer 被清理」 |
| **`total_deadline` 与 `max_attempts` 打架** | 6 个 attempt × 各自 TTFB 可能远超 120s | **必须有 per-attempt deadline**（复盘 P0-06），否则网关自己先挂死 |
| **半开连接竞态** | 客户端断连后 socket 未回收，同渠道 30s 内被重复占用 | 监听 `req.aborted`/`res.close`，主动 `reader.cancel()` 并标记渠道空闲（复盘 P0-11） |

**结论**：Fastify 完全能用，但在流式路径上**帮不上忙、还会添乱**。建议 `/v1/*` 数据面**绕开 Fastify**（裸 `http.createServer` 或严格用 `reply.raw` 分层），管理面继续走 Fastify。

### 1.4 better-sqlite3 在 Windows 打包的坑 —— 建议直接换 `node:sqlite`

better-sqlite3 是**原生 C++ 模块**，Windows 上的问题：每个 Node 大版本要不同 prebuild；打包/分发时 `.node` 必须一起带上且不被 `npm prune --production` 误删；需要 MSVC Build Tools 才能从源码编译，用户机器上编译失败 = 服务起不来；与打包链 ABI 冲突是经典坑。

| 方案 | 结论 |
|---|---|
| **`node:sqlite`（Node 22+ 内置）** | ✅ **首选**。零依赖、零 ABI 风险、打包就是纯 JS。本机 Node **v26.0.0 实测**：`DatabaseSync` API 齐全、`PRAGMA journal_mode=WAL` 生效、UDF（自定义函数）支持、事务正常、**20 万行批量插入 112ms**、聚合 7ms —— 对 IO 密集的 AI 网关绰绰有余 |
| **`libsql` / `@libsql/client`** | 备选。真 WASM/native 双实现、支持远程库，适合将来多节点。生态不如内置成熟 |
| **WASM（`sql.js`）** | ❌ 不建议。性能与持久化都不行，日志写入会成瓶颈 |

**但 `node:sqlite` 有 3 个实测坑，必须在数据模型里规避：**

1. **BIGINT 超过 2^53 直接抛异常**（不是返回字符串，也不是降精度）：
   > `select 9223372036854775807 as big` → `Value is too large to be represented as a JavaScript number`
   → **金额字段用「最小货币单位」的 INT**（如微美元），绝不让 token 总数/累计花费超过 2^53。详见 §5。
2. **没有 `db.backup()`**（实测 `typeof db.backup === "undefined"`，只有独立的异步 `backup()` 导出函数）。在线备份用 SQLite `VACUUM INTO 'backup.db'`（原子，推荐）或文件级复制 WAL/SHM（不原子）。
3. **WAL 下第二个写连接立刻 `SQLITE_BUSY`**（实测 `busy_timeout=0` 时 0ms 抛 `ERR_SQLITE_ERROR`）。→ **单写者模式**：配置/日志/统计同进程单连接串行写，或所有写走一个队列并设 `busy_timeout`。

> 本机 npm registry 不可达，`better-sqlite3` 能否在此机装 prebuild 我**没验证** —— 但不影响结论：`node:sqlite` 本机可用且足够快。

### 1.5 Tauri2 + Vue3 管理面连远程网关

**鉴权**：
- 管理密钥若远程传输，明文 HTTP 等于裸奔。**远程连接强制 HTTPS**（或走 SSH/Tailscale 隧道）。
- **双密钥分离**：数据面 key（客户端用、可多、可分租户）与 admin key（仅管理面用，**只在本机或受信网络使用**）。比对用 `crypto.timingSafeEqual` 防时序侧信道。
- Tauri 侧访问远程网关走系统 fetch，管理面**精确白名单 Origin**，禁止 `*` + credentials。

**实时推送**：仪表盘要「最近切换事件滚动条」「当前健康状态」。**SSE**（`/admin/api/events`）最简单，Vue 侧 `EventSource` 即可。别上 WebSocket —— SSE 够用且好穿透代理。**只推送状态与日志元数据，不推送 prompt/响应正文**（见 §4.4）。

**托盘/自启**：Tauri 2 的 autostart 插件只管**客户端**自身；**服务端**的 Windows 服务是另一件事（见 §3.6）。

### 1.6 Tauri 2「~10MB 安装包」承诺是否成立？

**部分成立，但方案里的数字不能当承诺。**
- 空壳 Tauri 2 应用用系统 WebView2（Win10/11 自带），exe 确实可以只有几 MB，装配后安装包通常在 ~5–15MB 量级 —— 这个量级可信。
- 但**本项目会明显变大**：Vue3 + **ECharts**（整包引入会显著推高体积，建议按需引入或换轻量图表库）。
- **本机没有 Tauri 成品 exe 可测**，所以我把「~10MB」当**空壳估算**，不作为承诺。

**建议**：M5 验收标准里写「安装包 ≤ X MB（实测）」，X 由第一次真实构建确定，别在方案里先写死。

## 2. 可测试性：「失败永不外漏」的测试体系

这是本项目**成败的分水岭**。缓冲-提交状态机的正确性**不可能靠功能测试/人工点测保证**，必须分层，且以「假上游矩阵」为核心。

### 2.1 四层测试

```
L1 表驱动状态机单测（毫秒级，无 IO）
   └─ 输入：一次 attempt 的「字节事件序列」→ 输出：FAIL / COMMITTED / POST_COMMIT_*
   └─ 不起真 socket，attempt() 纯函数化
L2 假上游集成测试（真 socket、真 fetch）        ← 本次原型这层
   └─ 起 N 个假上游 server，每个一种失败模式；网关配置指向它们
   └─ 真实跑降级链，断言客户端可见的一切
L3 端到端契约测试（真实 OpenAI SDK 打网关）
   └─ openai-python / openai-node 打 /v1/chat/completions，验证 SDK 不炸
L4 故障注入 / 混沌（长时间）
   └─ 随机 kill 上游、注入延迟抖动、制造 WAL BUSY、填满磁盘
```

**关键设计：L1 的 `attempt()` 必须是纯函数** —— 吃一个「字节流适配器」，吐决策。这样表能穷举几十种字节序列而不用为每种起真 server；**L2 只挑每类 1 个代表**做真 socket 验证（防止 L1 的假 adapter 掩盖半包、Nagle、超时等真实网络行为）。

### 2.2 假上游矩阵（11 种，原型已实现并跑通）

| # | 模式 | 触发 | 网关判定 | 客户端可见（有 ok 兜底时） |
|---|---|---|---|---|
| 1 | `ok_stream` | 正常 SSE，3 delta + `[DONE]` | COMMITTED | 完整内容 |
| 2 | `slow_but_ok` | 首事件晚 ~120ms 但正常 | COMMITTED | 完整内容 |
| 3 | `error_200_sse` | `200` + `data:{"error":{...}}` | FAIL `upstream_error_200` | 无感 |
| 4 | `error_200_json` | `200` + JSON error body | FAIL `upstream_error_200` | 无感 |
| 5 | `http_429` | `429` + Retry-After | FAIL `http_429` | 无感 |
| 6 | `http_500` | `500` | FAIL `http_500` | 无感 |
| 7 | `conn_refused` | 连不上的端口（:1） | FAIL `connect_error` | 无感 |
| 8 | `ttfb_hang` | `200` 头永不发，socket 挂着 | FAIL `ttfb_timeout` | 无感 |
| 9 | `stall_midway` | 发 1 delta 后静默 | FAIL `idle_timeout`（提交前） | 无感 |
| 10 | `bad_sse` | `data:` 后非 JSON | FAIL `malformed_json` | 无感 |
| 11 | `midway_disconnect` | 发内容后 socket destroy | POST_COMMIT | **见 §1.2，有 `finish_reason` 要求** |

还需补进 fixture 的（原型未覆盖，但方案会遇到）：
- `gzip` 压缩的 SSE（`Content-Encoding: gzip`）—— 解析前必须解压；
- HTTP/1.1 **chunked 畸形**（chunk 边界错误）；
- `200` 但中途 EOF 且缺 `[DONE]`（提交点 c 下必须判 FAIL）；
- `200` 首事件只有 `role` 无 `content`（验证 `sawContent` 判定不误杀）；
- `finish_reason: content_filter`（§0 表里的「内容风控」，验证可配开关）。

### 2.3 可执行验收清单（每条 = 给定 X 配置，当上游 Y，断言客户端看到 Z）

「配置」= 提交点 / 预算 / 降级链；「客户端看到」= status + content-type + **重组后的完整文本** + 是否有 `[DONE]`/`finish_reason` + 是否泄漏上游文案。

**A. 无感降级（有兜底 ok 渠道）—— 承诺「零泄漏、零破损」**

| # | 给定 | 当 | 断言客户端看到 |
|---|---|---|---|
| A1 | 提交点 a/b，链=`500,err200,ok` | 依次降级 | `200`+`text/event-stream`；重组=`tok1tok2tok3`；有 `[DONE]`；有 `finish_reason`；无 `gateway_exhausted`；**不含** `internal error`/`quota exceeded` |
| A2 | 提交点 a，链=`conn_refused,ok` | 连接拒绝后成功 | 同 A1 |
| A3 | 提交点 a，链=`err200sse,err200json,ok` | 200+error 后成功 | 同 A1 |
| A4 | 提交点 a，链=`bad_sse,empty_200,ok` | 非法 JSON + 空 body 后成功 | 同 A1 |
| A5 | 提交点 a，链=`stall_midway,ok` | 提交前卡死后成功 | 同 A1（重组文本来自 ok 渠道） |
| A6 | 提交点 a，链=`429,ok` | 429 后成功 | 同 A1 |
| A7 | 提交点 c，链=`stall_midway,ok` | 全量缓冲识别卡死后成功 | 同 A1，首字节晚于 a（可接受） |

**B. 预算耗尽 —— 承诺「一个干净错误」**

| # | 给定 | 当 | 断言客户端看到 |
|---|---|---|---|
| B1 | 提交点 a/b/c（**keep-alive 关**），链全死 `500,err200,ttfb_hang` | 预算耗尽 | `502`+`application/json`；body 可 `JSON.parse`；`error.type=gateway_exhausted`；含 trace id；**无 SSE 残留**；**无上游文案** |
| B2 | 同 B1 但**开 keep-alive** | 同 | **预期契约变更**：`200` + `data:{"error"}`，**不返回 502**（用于固化「选 B」后的行为） |
| B3 | `max_attempts=1`，链=`500,ok` | 只有一次机会 | `502`，且**客户端没拿到 ok 渠道的任何内容** |
| B4 | `total_deadline=1s`，上游都慢 | 触发总时限 | `502`（不是超时断连），且在 ~1s 内返回（不是最后一刻才有）—— 对应复盘 P1-13「预留窗口」 |

**C. 提交后断流 —— 承诺「结构合法」**

| # | 给定 | 当 | 断言客户端看到 |
|---|---|---|---|
| C1 | 提交点 a，链=`midway_disconnect` | 提交后断流 | `200`；重组=`Hello world`；有 `[DONE]`；**必须 `finish_reason`（stop 或 error）** —— 当前实现缺，必须补（§1.2） |
| C2 | 提交点 c，链=`midway_disconnect` | 全量缓冲识别断流 | `502`（不泄漏半截内容） |
| C3 | 客户端读到一半断开 | 客户端取消 | 网关及时 `reader.cancel()`、不泄漏 socket、不重复计费 |

**D. 非流式**

| # | 给定 | 当 | 断言 |
|---|---|---|---|
| D1 | `stream=false`，上游 ok | 正常 | 完整 JSON，`finish_reason`+`usage` 齐全 |
| D2 | `stream=false`，上游 `err200` 后 `ok` | 降级 | 完整 JSON 来自 ok；无上游 error 体 |
| D3 | `stream=false`，上游中途断 | 断流 | **完整 JSON 或干净错误，绝不是半截 JSON**（复盘 P0-02 场景 B） |

**E. 内部不变量（L1 单测，断言 attempt() 纯逻辑）**

| # | 断言 |
|---|---|
| E1 | 任何返回 `FAIL` 的路径，`res.write` **调用次数 = 0**、`headersSent = false` |
| E2 | `COMMITTED` 之后 buffer 内所有字节按序 flush，**无丢失无重复**（见下方实测 bug） |
| E3 | 每次 attempt 结束所有 timer 被 `clearTimeout`（无泄漏） |

> **E2 是原型实测抓到的真实 bug**：最初的提交实现里 `ok_stream` 客户端只收到 **1 个** SSE 事件（应为 6 个）—— 提交后的事件被缓冲逻辑吞掉了。这类「内容静默丢失」**不会被任何只断言 status=200 的功能测试发现**，只能靠重组文本逐字比对抓到。

**F. 性能/稳定性（L4）**

| # | 断言 |
|---|---|
| F1 | 100 并发流式请求，网关 RSS 不无界增长（背压生效） |
| F2 | 上游半开连接不响应，chunk idle timer 能把它踢掉并降级 |
| F3 | 连续 1000 请求后 SQLite 不 `SQLITE_BUSY`（写队列生效）、库不涨到 GB（日志滚动生效） |

### 2.4 故障注入清单

- **网络**：随机 RST 上游连接、注入 0–5s 抖动、把 TTFB 拉到超时阈值上下边界；
- **进程**：随机 kill 一个假上游、kill 服务端后重启（验证崩溃恢复与 WAL 完整性）；
- **资源**：填满磁盘（验证日志上限）、制造 WAL BUSY；
- **配置**：热更新时并发打请求（验证配置快照原子性，复盘 P1-25）。

## 3. 运维能力

### 3.1 健康与就绪端点

| 端点 | 语义 | 用途 |
|---|---|---|
| `GET /healthz` | 进程活着即 200（**不查依赖**） | 存活探针（Windows 服务 / LB） |
| `GET /readyz` | SQLite 可读写 + 配置已加载才 200 | 就绪探针（启动中、未连上 DB 时返回非 200） |
| `GET /metrics` | Prometheus 文本格式 | 监控 |

**`/metrics` 最少导出**（直接对应核心承诺的可观测性）：
```
gateway_requests_total{status,model,channel}         # 客户端视角成功/失败
gateway_attempts_total{channel,outcome,error_class}  # attempt 维度（复盘 P0-05）
gateway_exhausted_total                              # 预算耗尽次数（核心承诺的失败率）
gateway_channel_cooldown_seconds{channel}            # 冷却中的渠道
gateway_request_duration_seconds{phase=precommit|postcommit}
gateway_upstream_cost_usd_total                      # 上游真实花费（含失败 attempt）
```

### 3.2 结构化日志 + trace_id 全链路贯穿

**「失败不外漏」要能被排查，trace_id 是唯一抓手。**
- 每个入口请求生成 `trace_id`。**响应头返回 `X-Gateway-Trace-Id`**；错误体的 `message` 里也嵌 trace（如方案所写 `trace: xxx`），用户截图报错即可反查完整链条。
- 客户端带来的 `X-Request-Id` **记入日志但不复用为上游幂等键** —— 复盘 P0-09：透传它会让上游去重静默毁掉所有降级。
- 每个 attempt 记 `attempt_no`；每次失败记一条**切换事件**。
- **切换日志页就是 trace 的物化**：一条 request 串起 N 条 switch，每条含 `ts, trace_id, attempt_no, tier, channel_id, upstream_model, error_class, upstream_status, latency_ms`。

### 3.3 日志保留与磁盘上限

- **保留策略分层**：请求日志保留 N 天（默认 7–14）、切换日志同、**统计聚合永久**（见 §5）。
- **磁盘硬上限** `max_db_bytes`（默认如 2GB）。写入前检查，超限则先删最老切换日志，再告警 —— **绝不能让磁盘写满把整个网关搞挂**。
- **清理机制**：定时任务执行，**不要在请求路径里删**。按自增 `id` + 时间索引分批删，避免长事务阻塞。
- 日志表与配置表可**分库**（复盘 P1-26），降低互相拖累。

### 3.4 配置导入/导出与备份

- **导出** `GET /admin/api/config/export` → 单个 JSON（配置 + 分组 + 渠道 + 模型映射 + 价格），带 schema 版本号。**默认不含明文密钥**（用指纹 + 后 4 位）。
- **导入**：向后兼容迁移；导入前自动备份；导入后校验（渠道可达性、模型名非空、循环参数合法）。
- **备份**：见 §1.4 第 2 点 —— `node:sqlite` 无 `db.backup()`，用 `VACUUM INTO 'backup.db'`（原子、在线）。提供 `POST /admin/api/backup` + 计划任务。**这是必须的手动验证项。**

### 3.5 数据库迁移与升级路径

- **迁移**：启动时检查 `PRAGMA user_version`，按序执行 `migrations/NNN_xxx.sql`，每条包在一个事务里；**迁移前自动 `VACUUM INTO` 备份**。
- **升级路径**：服务端「新版本先跑迁移 → 重启 → readyz 通过」，停机窗口 = 迁移耗时（应 <1s）。
- **客户端与服务端版本解耦**：客户端只依赖管理 API 的稳定子集，服务端向后兼容旧客户端。
- **崩溃恢复**：SQLite WAL 本身抗进程崩溃。重启后未完成的流式请求（客户端也已断），无需补偿；但**必须**把「尝试中写入」改为「完成后写入 + 补偿删半成品」，避免崩溃留下脏 attempt 行。

### 3.6 优雅停机与崩溃恢复

监听 `SIGINT`/`SIGTERM`：
1. `/readyz` 立即返回非 200（让 LB / 服务管理器摘流）；
2. 停止接受新连接，**给进行中的流一个宽限期**（如 10–30s）让它们写完 `[DONE]`；
3. 超时未完的连接主动关闭；
4. flush SQLite、关连接、退出。

**Windows 服务**：推荐 **NSSM** 或 **任务计划程序（触发器 = 系统启动）**。NSSM 有现成工具（本机未装，需自备）；任务计划无需额外二进制、最简单，代价是控制台交互弱。

## 4. 安全

### 4.1 密钥存储

| 场景 | 方案 |
|---|---|
| **Windows 本机** | **DPAPI**（`CryptProtectData`）加密存储，服务端用当前用户（或服务账户）解密。零依赖、与 OS 绑定、开机自动可用。⚠️ 本机沙箱受限，我**未能实测 DPAPI 可用性**，落地时需在目标机验证（尤其以服务账户运行时） |
| **跨平台 / 远程网关** | 应用层对称加密（AES-256-GCM），主密钥来自环境变量或主密钥文件（文件本身用 DPAPI / 系统钥匙串保护） |
| **数据库里** | **绝不存明文**。存 `secret_enc` + `nonce`；所有日志与导出**永不**把密钥载入应用层对象 |

- **密钥轮换**：每渠道支持多个 key（轮换期并存），见 §5。
- **比对**：`crypto.timingSafeEqual` 防时序侧信道。

### 4.2 管理面暴露面与 CORS

- **默认只监听 `127.0.0.1`**；要局域网/公网必须显式配置 bind address。
- **强制 HTTPS**：远程连接时 admin key 走明文 HTTP = 裸奔。要么内网只读 + 防火墙，要么 Tailscale/WireGuard/SSH 隧道。
- **CORS**：**精确 Origin 白名单**，禁止 `origin: true`（等价 `*` + 回显），禁止 `credentials: true` 与通配符并用。管理面默认 `credentials: false`。
- **admin key 与数据面 key 分离**，权限最小化；管理 API 不接受数据面 key。
- **限流**：`/admin/*` 加 IP 限流（密钥类接口尤其）。

### 4.3 日志脱敏

进入日志/切换日志前统一过脱敏器：
- `Authorization`、`api-key`、`x-api-key`、`Cookie`、`Set-Cookie` → 全部替换为 `[REDACTED]` 或「指纹 + 后 4 位」；
- **请求/响应正文（prompt / completion）默认不入日志**。

### 4.4 请求体留存策略与采样

| 数据 | 策略 |
|---|---|
| 请求元数据（method/path/status/耗时/token/渠道） | **全量留存**（无正文） |
| 请求/响应正文 | **默认不留**。开关 `debug_capture_body` 开启后按**比例采样**（如 1%）+ 脱敏 + 独立表 + 7 天 TTL + 明确 UI 提示 |
| 切换原因（error_class） | **全量留存**（核心资产，不含正文） |

**绝不把 prompt / 响应全文写进主日志表** —— 那是隐私炸弹，且体积爆炸。

## 5. 成本核算数据模型

这是方案 §5「统计」页的地基，**字段现在定好、后面难改**。要解决：多 Key、多币种、缓存命中 token 计价、失败尝试的成本口径、按模型/渠道/分组/租户归因。

```sql
-- 渠道（一个渠道可有多个 key，用于轮换）
channels(id, name, base_url, protocol, enabled,
         currency TEXT DEFAULT 'USD',        -- 渠道结算币种
         created_at, updated_at);

-- 渠道下的 API key（密文）
channel_keys(id, channel_id,
             secret_enc BLOB, nonce BLOB,     -- DPAPI/AES 密文，绝不明文
             key_fingerprint TEXT,            -- 日志展示用指纹
             label TEXT,                      -- '主key'/'备用key'
             enabled, weight, cooldown_until,
             last_used_at, disabled_reason);

-- 对外模型 + 价格（价格带生效期，支持调价不丢历史）
model_pricing(id, external_model, upstream_model, channel_id,
              currency TEXT,                   -- USD / CNY / ...
              unit TEXT,                       -- 'per_1M_tokens'
              in_price_per_unit REAL,
              out_price_per_unit REAL,
              cache_read_price_per_unit REAL,  -- prompt_cache 命中价（远低于 in）
              cache_write_price_per_unit REAL,
              effective_from, effective_to);

-- 分组（= 租户）
groups(id, name, monthly_budget_usd, rate_limit_rpm, enabled);

-- ★ 每次 attempt 一行（复盘 P0-05 的核心：attempt 粒度）
attempts(id, trace_id, group_id, external_model,
         attempt_no INT, tier INT, cycle INT,
         channel_id, channel_key_id, upstream_model,
         -- 结果
         status TEXT,          -- committed / precommit_failed / post_commit_failed
         error_class TEXT, upstream_status INT,
         ttfb_ms, latency_ms, committed BOOLEAN, post_commit_break BOOLEAN,
         -- 计费（对齐上游 usage，缺则估算）
         prompt_tokens INT, completion_tokens INT,
         cached_read_tokens INT DEFAULT 0, cache_write_tokens INT DEFAULT 0,
         usage_source TEXT,    -- 'upstream' | 'estimated'
         cost_minor BIGINT, cost_currency TEXT,   -- 最小货币单位（规避 BIGINT 坑）
         upstream_billed BOOLEAN,  -- 上游是否大概率已计费（对账用）
         created_at);

-- 聚合表（统计页只查这张，保证性能）
stats_daily(day, group_id, external_model, channel_id,
            requests, success, exhausted,
            prompt_tokens, completion_tokens, cached_read_tokens,
            cost_minor, currency,
            PRIMARY KEY(day, group_id, external_model, channel_id));
```

### 5.1 关键口径（写进文档，形成共识）

1. **缓存命中 token（`prompt_cache`）**：Anthropic 等对「缓存读取」给**大幅折扣价**，缓存命中不按普通输入计费。故 `prompt_tokens` 必须**拆成 `prompt_tokens`（未命中部分）+ `cached_read_tokens`**。上游 `usage` 里的 `cache_read_input_tokens` 映射到 `cached_read_tokens` 并按 `cache_read_price` 计价。**否则缓存命中率高的用户会被多算 5–10 倍钱。**
2. **多币种**：所有 `cost_*` 带 `currency`。统计页默认折算 USD（用可配置汇率表），**保留原币种以便对账**。汇率表要存 `date`，否则历史统计会随汇率变动而漂移。
3. **失败尝试的成本口径**（与复盘 P0-05 一致）：
   - **提交前失败的 attempt**：上游可能仍计费（已开始生成才超时）→ 计入 `upstream_cost`，但**不计入用户账单** `billed_cost`；单独做「浪费成本」面板。
   - **提交后失败**：内容已给客户端，**按已产出 token 计费**。
   - 用户账单 = Σ(committed attempts)。提供响应头 `X-Gateway-Upstream-Attempts` / `X-Gateway-Upstream-Cost`，让 Claude Code 这类会展示成本的客户端能显示真实开销。
4. **归因维度**：模型 / 渠道 / 分组（=租户）/ 日。四维都在 `stats_daily` 里，统计页直接 group by，**不实时扫 attempts**。
5. **BIGINT 安全**（§1.4）：`cost_minor` 用 **INT 微单位**（如「微美元」= 1e-6 USD），单条 attempt 最大约 1e6 微单位，远小于 2^53。**累计值在 SQL 里聚合，绝不在 JS 里累加。**

## 6. 里程碑重排 M1..M5

原方案 M1–M5 偏「按模块切」（先服务端、再客户端、再统计、最后打包）。问题：**核心承诺的验证被推迟到很晚，且打包/运维留到最后风险大**。按「**先证核心 + 测试先行 + 运维提前**」重排：

| 里程碑 | 目标 | 内容 | 可演示验收标准 |
|---|---|---|---|
| **M0**（新增，约半周） | **锁定承诺的精确定义** | 书面裁决提交点语义；定两条终态路径（未发头 = 502 JSON / 已发头 = 200 + error frame）；定义 `finalizeError` 单一出口与 `headersFlushed` 不变量；建 L1 状态机骨架 + 本文 §2.2 的 11 种假上游 fixture | ①「提交前发 keep-alive」的歧义被**书面裁决**（选 A 或 B）；② 假上游 fixture 能一键起 11 种模式；③ L1 状态机单测可跑 |
| **M1** | **核心代理可跑（CLI）** | 缓冲-提交代理 + 路由循环 + 冷却 + 切换日志 + **`finalizeError` + `headersFlushed` 不变量**。**此时就接上 L2 集成测试与验收清单 A/B/C/E** | ① 假上游矩阵全绿：A1–A7 重组文本逐字正确、B1/B3/B4 拿到干净 502（keep-alive 关）、C1 有 `finish_reason`、E1/E2/E3 不变量成立；② 用真实 OpenAI SDK 打网关跑通一次正常流；③ 记录跑通的命令行 |
| **M2** | **服务端功能完整 + 基础运维** | 管理 API + SQLite（**用 `node:sqlite`**）+ `/v1/models` + 整流器 v1 + headers 透传；**外加** `/healthz` `/readyz` `/metrics`、trace_id 贯穿、结构化日志、日志滚动与磁盘上限、`user_version` 迁移、`VACUUM INTO` 备份 | ① 管理 API CRUD 后请求**即时走新渠道**；② 停掉 SQLite → `/readyz` 非 200；③ 灌 10 万条日志 → 库不超上限、旧日志被清；④ `VACUUM INTO` 产出的备份可被独立进程打开；⑤ 导出 → 导入 → 配置等价 |
| **M3** | **Tauri 客户端** | 六个页面 + 托盘 + 自启；远程连网关（双密钥 + CORS 白名单 + 强制 HTTPS 提示）；SSE 实时推送健康/切换事件 | ① 六个页面可用，仪表盘数字与 `/metrics` 一致；② 远程网关能连上并改配置，**http 明文远程被拒**；③ 切换日志页能按 trace_id 串出完整链条；④ **实测安装包大小并记录** |
| **M4** | **统计/成本闭环 + 故障注入** | 统计页（ECharts）+ 价格 + **attempt 粒度计费** + 多币种/缓存 token 计价 + 「浪费成本」面板；跑一轮 L4 混沌 | ① 按模型/渠道/分组/日出图，含 cached token 拆分；② 「浪费成本」面板能指出哪个渠道在提交前反复烧钱；③ L4 跑完：100 并发不 OOM、半开连接被踢、WAL 不 BUSY |
| **M5** | **打包交付 + 文档** | 服务端 Windows 服务/任务计划自启 + 优雅停机 + 崩溃恢复；客户端安装包；**运维手册**（备份/恢复/迁移/停机/排障）+ API 文档 | ① 服务端开机自启，kill 后自恢复且数据无损；② 优雅停机时进行中的流正常收尾；③ 客户端安装包在干净 Win10/11 装上能连本机 + 远程网关；④ **让一个没参与开发的人照着手册完成「备份 → 重装 → 恢复」**；⑤ 全量验收清单 A–F 全绿 |

**为什么这样切：**

- **M0 提前解决歧义**：§1.1 的 keep-alive 矛盾、提交后终态语义，若留到 M1/M2 才发现，后面全要返工。**先书面裁决再写码。**
- **M1 就接 L2 测试**：核心承诺不能「写完再测」，验收清单 A/B/C/E 就是 M1 的 Definition of Done。
- **运维提前到 M2**：`/healthz` `/readyz` `/metrics`/日志/迁移/备份拖到 M5 太晚 —— M2 一旦数据库出问题没这些手段会抓瞎。`node:sqlite` 的 BIGINT / 无 backup / WAL BUSY 三坑必须在 M2 就设计对。
- **打包留 M5，但自启/停机要早测**：真正卡人的是 Windows 服务化，放最后风险高，所以 M5 把它列为头号验收项。
