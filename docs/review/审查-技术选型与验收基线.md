### 0.1 【致命】方案 §6 写的「Node.js 20」**已经 EOL 半年了**

| 22 | v22.23.3 | Jod | 2027-04-30 | 🟢 可用 |

Node 20 最后一个小版本停在 **2026-03-24**，之后再无安全更新。方案选它，等于**新项目一开工就站在没有安全补丁的运行时上**。

> **必须改成 Node 22 LTS 或 24 LTS，推荐 24**（Krypton，EOL 2028-04-30，还有 19 个月）。

### 0.2 【关键】better-sqlite3 v13 已经**解决了** Windows 打包问题 —— 方案写的是旧认知

| 版本 | engines | install 脚本 | 打包方式 | unpacked |
|---|---|---|---|---|
| 12.11.1 | 20.x … 26.x | prebuild-install 或 node-gyp | 运行时从 GitHub **下载** prebuild | 9.9 MB |
| **13.0.3** | **>=22** | **（空）** | **8 平台 prebuild 全部内联** | 26 MB |

我下载 v13.0.3 的 tarball 实测（11,402,131 字节 / 68 个条目）：

    package/prebuilds/win32-x64.node       1.90 MB   <- 目标机器直接命中
    package/prebuilds/linux-x64.node       2.12 MB
    package/prebuilds/darwin-arm64.node     1.89 MB
    ... 共 8 个平台，prebuilds 目录合计 16.1 MB

lib/binding.js 的加载逻辑（实测源码）：

    let filename = getPrebuildPath();      // 直接 require 内联 .node
    if (filename) return DEFAULT_ADDON = require(filename);
    // 只有找不到才退回 node-gyp 的 build/Release

**含义**：v13 在 Windows 上 **零编译、零网络下载、零 node-gyp**，npm i 完就能跑。这正是兄弟稿担心的「坑」的解药 —— 官方已经解决了。

**但代价是 engines >= 22**，又反过来锁死 Node 20。**§0.1 和 §0.2 是同一个决定的两面：必须放弃 Node 20。**

> **决策：Node 24 LTS + better-sqlite3 ^13.0.3。** 二者强绑定，不能只要一个。

### 0.3 反过来，被迫留在 Node 20 —— 打包链会真的断

v12.x 走的是 prebuild-install 或 node-gyp rebuild。prebuild-install 从 GitHub Releases 拉二进制，拉不到就退回本地编译，而 node-gyp 需要 MSVC。

**本机实测：**
- GitHub API 直连 → **403 已禁止**（企业网络 / 代理常见）
- cl.exe → **NOT on PATH**（没有 VS Build Tools）

即：**预编译下载失败 + 本地没有 C++ 编译器 = 安装直接失败**。这就是「Windows 打包坑」的真实成因 —— 它是**网络与工具链问题，不是 SQLite 驱动本身的问题**。升到 v13 就整条绕开了。

### 0.4 体积承诺：「~10MB」只对客户端成立，方案没说服务端

方案 §6 的 ~10MB 是 **Tauri 客户端**。但服务端要装 Node 运行时：

| 组件 | 实测 / 估算 |
|---|---|
| node.exe（v26，本机实测） | **93.4 MB** |
| node.exe zip 压缩后（实测 Compress-Archive Optimal） | **34.7 MB** |
| node_modules（fastify + undici + pino + better-sqlite3 + zod） | 约 45-60 MB |
| better-sqlite3 unpacked（v13，含全平台） | 26 MB（实际只用 1.9 MB） |

**服务端交付体积约 120-160 MB，客户端约 10 MB。** 方案只承诺了后者，等于**隐含承诺了「服务端零安装」，而这是假的**。

而且 node:sqlite 虽免了 26 MB 的多平台 prebuild，但 **Node 运行时本体这 93.4 MB 谁都省不掉**（除非换 Go / Rust 重写服务端）。

> **要么在文档里把「两个成品、各自多大」写清楚，要么评估 Go 单二进制（约 25 MB，零运行时）—— 这是 §6「备选」里唯一真正能兑现「小体积」的选项。**

### 0.5 node:sqlite 可用，但少一个 API

实测（Node v26.0.0）：

    WAL -> journal_mode=wal            OK    文件库正常
    in-tx read count = 1               OK    事务内可见
    lastInsertRowid type: number 2     OK    是 number 不是 bigint
    function: function                 OK    自定义函数可用
    aggregate: function                OK    自定义聚合可用
    backup: undefined                  没有 db.backup()

**结论**：node:sqlite 在 Node 24 / 26 上完全够用，唯一缺口是 **backup() 不存在** → 备份 / 导入导出改用 **VACUUM INTO**（SQLite 3.27+ 原生、单文件快照、不锁库）。这比兄弟稿建议的绕法更干净。

| 选项 | 结论 |
|---|---|
| **better-sqlite3 ^13** | ✅ **首选**。API 最全、零编译、v13 已内联 prebuild。配 Node 24 |
| node:sqlite | 🟡 备选。省 26 MB，但少 backup()、绑死 Node >= 22 / 24 |
| libsql / WASM | 🔴 **不必要**。libsql 为边缘同步设计，本地单机是杀鸡用牛刀且引入网络依赖；WASM 慢一个数量级 |

## 1. 技术选型风险补充

### 1.1 Node + Fastify 流式网关：真正的坑不是「流式」，是**两套超时 / 两套栈**

兄弟稿 P1-23 说了「流式与非流式配置必须分离」，这里补上**具体的数**（当前生态默认约束）：

- @fastify/sse 0.6.1 要求 node >= 20.20.2
- **undici 8.11.2 要求 node >= 22.19.0**
- **vitest 5.0.3 要求 ^22.12 或 ^24 或 >=26**

**Node 24 LTS 全部满足。vitest 5 直接不支持 Node 20** —— 又一个必须放弃 Node 20 的硬证据。

**落地清单：**

1. maxRequestsPerSocket / keepAliveTimeout / headersTimeout 三者必须满足 headersTimeout > keepAliveTimeout > 0，否则 Node 直接拒收连接。
2. 流式端点用 reply.hijack() 或 @fastify/sse，**不要**让 Fastify 的序列化器碰流；非流式端点单独一组超时配置。
3. **必须显式 X-Accel-Buffering: no + Cache-Control: no-cache**（呼应 P0-12）。
4. 背压：reader.read() 循环里必须判断 res.write() 返回值与 drain，否则慢客户端 = 内存无界（呼应 P1-22）。

### 1.2 Tauri2 + Vue3 管远程网关

本机 Rust 环境实测：x86_64-pc-windows-msvc 目标已装，cargo 1.99 —— Tauri 构建链可用。插件版本：@tauri-apps/api 2.12.3、plugin-autostart 2.7.0、plugin-updater 2.13.3。

**风险点（方案完全没提）：**

- **Tauri 2 的 capability / 权限模型默认是「拒绝」。** 客户端要发 HTTP 到**远程**网关，需在 capabilities/*.json 里显式声明远程 origin，否则运行时报权限错误 —— 而这个错误只在真机远程模式下出现，本地调试发现不了。**必须第一周就把「远程模式」跑通，别留到最后。**
- **明文 HTTP 会触发混合内容拦截。** 远程网关若是 http://192.168.x.x，Tauri（WebView2）按安全策略可能直接拦。要么强制 HTTPS，要么在 capability 里显式放开 + 明确告知用户「仅限可信内网」。
- 管理密钥不能进前端 localStorage 明文；应走 Tauri **stronghold / OS keychain**，或至少保证管理密钥只在 Rust 侧使用、由 Rust 发请求不经 JS。

## 2. 「失败永不外漏」的可执行验收基线

这是本文最该被拿走用的部分。**我实际写了代理原型 + 11 种假上游跑通，并抓出两轮真实泄漏**（见 §2.2）。

### 2.1 分层测试

| 层 | 工具 | 覆盖 | 门槛 |
|---|---|---|---|
| L1 状态机单测 | vitest，**表驱动** | 纯函数：候选选择、冷却、预算扣减、提交判定 | 分支覆盖 > 90%，状态机 100% |
| L2 假上游矩阵 | node:http 造的假上游（**11 种，§2.2**） | 端到端「上游 → 客户端看到什么」 | **全绿，零泄漏** |
| L3 集成 | 真跑网关 + 真 SQLite | 鉴权、日志落库、统计口径 | 全绿 |
| L4 故障注入 | 断链、强杀进程、磁盘写满 | 崩溃恢复、优雅停机 | 手工，每次发布前 |

### 2.2 假上游矩阵（11 种）—— 我的原型实测结果

我把 §2.2 的提交点机制实现出来跑了矩阵，**第一版有真实泄漏**：

| # | 上游行为 | v1 朴素实现 | v2 加分类器 | **v3 修正后** |
|---|---|---|---|---|
| 1 | 正常流 | ✅ | ✅ | ✅ |
| 2 | 拒连 socket.destroy() | ✅ | ✅ | ✅ |
| 3 | 连接上但永不响应 hang | ✅ 800ms 超时 | ✅ | ✅ |
| 4 | TTFB 超时（首字节 5s） | ✅ | ✅ | ✅ |
| 5 | HTTP 500 + JSON 错误体 | ✅ | ✅ | ✅ |
| 6 | **200 + 首事件是 error** | ❌ **泄漏** upstream internal | ✅ | ✅ |
| 7 | **200 + error 帧后紧跟内容帧** | ❌ **泄漏** rate limited | ✅ | ✅ |
| 8 | 200 + 非 SSE 垃圾 | ⚠️ 透传了垃圾原文 | ❌ **透传垃圾** | ✅ |
| 9 | 200 + 空 body | ✅ | ❌ **透传空** | ✅ |
| 10 | 200 + 只有 role 无 content | ✅ | ✅ | ✅ |
| 11 | **提交后中途断流** | ⚠️ 只有 DONE 无 finish_reason | ⚠️ 同 | ✅ 有 finish_reason=error |

**三次泄漏的根因（可复用的教训）：**

1. **提交点判定必须「先分类、后提交」。** 朴素实现一看到内容 delta 就提交，于是「error 帧 → 内容帧」这种脏上游把错误文案先送出去了。**正确顺序：先 classify(buf)，确认无 error / 非法 JSON，再判提交。**
2. **流结束时必须校验「解析出了几个合法事件 / 有没有内容 delta」**，否则 0 事件或纯垃圾会被当成正常流放行。
3. **中途断流不能只补 DONE。** 只补 DONE 会让客户端以为**成功结束**，实际答案是被截断的 —— 这是**静默数据损坏**，比报错更糟。必须补 finish_reason=error + 标准 error 帧（呼应兄弟稿 §1.2）。

**v3 全部 11 项零泄漏**，实测输出样例：

    error_first  -> data: {error:{type:gateway_exhausted, code:upstream_error_event}} | data: [DONE]
    garbage      -> data: {error:{type:gateway_exhausted, code:not_sse_garbage}}     | data: [DONE]
    midstream_cut-> data: {内容...} | data: {choices:[{delta:{},finish_reason:error}], error:{...}}

> ⚠️ **泄漏检测必须是自动断言，不能靠人眼看 body。** 判定式：对客户端可见字节做正则匹配上游错误文案 / 上游 key / 上游错误码，命中即 fail。这条断言要进 CI。

### 2.3 可执行验收清单（给定 X 配置 → 上游 Y → 断言客户端看到 Z）

格式：**给定 / 当 / 断言**。每条可直接翻成测试用例。

**A. 提交点前失败不外漏**

| # | 给定 | 当 | 断言 |
|---|---|---|---|
| A1 | 3 渠道，A=500、B=拒连、C=正常 | 发 stream:true | HTTP 200 + text/event-stream + 完整 DONE + finish_reason=stop；内容完整无缺；**响应字节不含 500 / ECONNREFUSED** |
| A2 | 同上，A=200+error 体 | 同上 | 同 A1；且切换日志有 A 的 upstream_error_event |
| A3 | 同上，A=200+非 SSE 垃圾 | 同上 | 同 A1；切换日志 not_sse_garbage |
| A4 | 全部 3 渠道全失败 | 同上 | **200** + SSE error 帧 type=gateway_exhausted + DONE；**响应含 trace_id**；客户端拿到 0 个 content delta |
| A5 | 全部渠道全失败 | stream:false | **HTTP 502** + 合法 application/json + error 对象；**响应体不含任何上游文案** |
| A6 | max_attempts=6 | 6 渠道全失败 | 切换日志**恰好 6 条**；**第 7 次不发请求**（用假上游计数器断言） |

**B. 提交后失败（唯一允许有感知的场景）**

| # | 给定 | 当 | 断言 |
|---|---|---|---|
| B1 | 正常渠道，中途断流 | 上游发 2 帧后 destroy() | 有 finish_reason=error + 标准 error 帧 + DONE；**不是**裸断连；**不是**只有 DONE |
| B2 | 同上 | 同上 | 客户端 finish_reason **不等于** stop（防止被当成功入库） |

**C. 超时与预算**

| # | 给定 | 当 | 断言 |
|---|---|---|---|---|
| C1 | total_deadline=5s，每 attempt TTFB=3s | 上游 hang | 请求在 **5s 以内**返回，attempt 数不超过 2 |
| C2 | 同上 | 同上 | **不出现**「deadline 到了却什么都没返回」 |
| C3 | 提交前窗口 3s | 客户端 httpx read=5s | 网关**先**返回，客户端**不**先抛 ReadError |

**D. 幂等与重放（呼应 P0-03）**

| # | 给定 | 当 | 断言 |
|---|---|---|---|
| D1 | 客户端自带 X-Request-Id | 发生 2 次降级 | **第 2 次不透传同一个 request-id 给上游**（否则上游幂等去重会让降级全废） |

**E. 成本与统计（呼应 P0-05）**

| # | 给定 | 当 | 断言 |
|---|---|---|---|
| E1 | 3 次 attempt 都被上游计费 | 最终成功 | 统计里 **3 条** attempt 记录、**1 条** request 记录；费用 = 3 次之和 |
| E2 | 同上 | 同上 | 日志页能按 request_id 串出完整链条 |

### 2.4 故障注入清单

- 上游连接中途 RST / 半开（发一半 FIN）
- 上游返回 Content-Encoding: gzip 但 body 是坏的
- 上游 SSE **缺 DONE** 就 200 结束
- 上游 chunked 畸形（声明长度与实际不符）
- 磁盘写满（日志写失败）
- 强杀网关进程（-9），重启后 SQLite 是否恢复
- 网关运行中改配置（热更新原子性）

## 3. 运维要点补充

兄弟稿 §3 已覆盖得很完整，这里只补**本次核实出来的可执行细节**：

| 项 | 结论 |
|---|---|
| **备份** | backup() 不存在（实测）→ 用 VACUUM INTO。执行前先 wal_checkpoint(TRUNCATE) 再 VACUUM INTO 才是完整快照 |
| **数据库位置** | **必须放 ProgramData / 用户数据目录，不要放安装目录**。装到 C:\Program Files 会因 UAC 无法写 WAL |
| **迁移** | v13 内联 prebuild 后无 C++ 依赖，**升级 = 换 node_modules 整包替换**，比 node-gyp 时代安全 |
| **优雅停机** | WAL 模式下停机前务必 wal_checkpoint(TRUNCATE) + db.close()，否则 -wal 残留 |
| **磁盘上限** | WAL 会持续增长；设 wal_autocheckpoint + 定期 VACUUM，并对日志表做保留期清理 |
| **单写连接** | 兄弟稿实测「WAL 下第二个写连接立刻 BUSY」—— **确认属实**。必须全局单写连接 + 写队列 |

## 4. 安全要点补充

### 4.1 密钥存储：两个常见的 npm 包都是死包

查证结果：

- **win-dpapi 1.1.0，最后发布 2020-06-13**（6 年未更新）→ 弃用
- **keytar 7.9.0，最后发布 2022-02-17** → 已废弃，不建议新项目用

**正确做法：**

- **Tauri 侧**用 plugin-stronghold / OS keychain（Windows DPAPI 由 Rust 侧封装）
- **Node 服务端侧**用 Windows CNG（ncrypt.dll）或直接 FFI 调 CryptProtectData

**实测备注**：本机 PowerShell 5.1 在当前受限环境下无法加载 System.Security.Cryptography.ProtectedData 程序集（CryptographicServiceProvider 同样不可见，仅 RNGCryptoServiceProvider 可用）。这是**本机沙箱环境限制，不代表 Windows 上 DPAPI 不可用**—— 但它恰好说明一件事：**不要假设任何加密 API 在目标机器上一定可用，必须有降级路径和启动自检**。

> 建议：服务端启动时做一次密钥加解密自检，失败就**明确拒绝启动并报出原因**，而不是在第一次真实请求时才炸。

### 4.2 其余

- **管理面默认只绑 127.0.0.1**；要远程必须显式配置 + 强制 HTTPS + 独立管理密钥（不要复用分组密钥）
- **CORS 默认拒绝**；只有明确配置了允许的 origin 才放行
- **日志脱敏**：Authorization / api_key / x-api-key / sk- 前缀一律替换；**注意 /admin/api/logs 返回体也要脱敏，不能只脱敏写入侧**
- **prompt 留存**：默认**不落库**；如需排障，显式开关 + 自动过期（如 7 天）+ 可按分组关闭。**默认不存是最安全的默认值**

## 5. 成本核算：字段清单（可直接进 schema）

| 字段 | 说明 |
|---|---|
| request_id / attempt_no | **一请求多 attempt**，必须分开两张表或带 attempt_no |
| billed / billable_reason | 该 attempt 是否被上游计费（失败也可能扣钱） |
| usage_prompt_tokens / usage_completion_tokens | 分开 |
| **cached_prompt_tokens** | **prompt_cache 命中部分，单价不同，必须独立字段** |
| cache_creation_tokens | 部分厂商缓存写入单独计价 |
| reasoning_tokens | 推理模型 token 单价不同 |

**口径三条**：① 失败 attempt 也可能计费 → 按 billed 记账；② 价格必须快照；③ 真 / 估算 usage 分开统计。

## 6. 里程碑重排（含必须前置的技术决策）

原方案 M1..M5 顺序合理，但**缺了「选型定案」这一步**，且 M5 打包放在最后太晚。建议：
