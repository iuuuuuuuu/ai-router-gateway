## D01 · 服务端用 Rust，不用 Node（2026-10-13 · v0.1.0 起）

**决策**：服务端用 Rust（axum + reqwest + rusqlite），产出单文件 exe。

**为什么**：需求是「轻量、占用小、速度快」。同口径实测（本机 Windows x64）：

| 指标 | Rust(axum+reqwest+rusqlite) | Node(裸 http 基线) |
|---|---|---|
| 可执行文件 | **3.05 MB** | 93.42 MB（node.exe 本体） |
| 常驻 RSS | **6.19 MB** | 63.62 MB |
| 冷启动 | **343 ms** | 405 ms |
| 外部运行时 | 无（单文件） | 需装 Node |

Node 那列是**裸 http server**（未装依赖）；真实 Fastify + SQLite 组合只会更大（node_modules 另需 45–60 MB）。

**排除了什么**：
- **Node + Fastify**：不仅体积，还有「两套超时 / 两套栈」的流式风险，以及 Node 20 已 EOL 的打包链问题（见 [review/审查-技术选型与验收基线.md](review/审查-技术选型与验收基线.md)）。
- **better-sqlite3**：Windows 打包坑；即便新版已修，也不改变上面的大方向。
- **node:sqlite**：少一个 API，且仍绑在 Node 运行时上。

**何时该翻案**：Rust 单文件体积/RSS 不再有优势（例如换成必须带 JVM/.NET 运行时的方案），或团队完全无法维护 Rust 代码。**只要「单文件零依赖 + 个位数 MB」还是硬需求，就不翻案。**

## D02 · 提交点之前对客户端零字节，保活走 TCP 层（2026-10-13 · 纠正 v0.2 的设计）

**决策**：流式请求在收到**第一个合法内容帧**之前，绝不向客户端 socket 写任何字节。**不写 ` : keep-alive` 注释帧。**

**为什么**：v0.2 曾写「重试期间发 `: keep-alive`」保活。**实测证明它摧毁核心承诺**：一旦写出首字节，HTTP 头就落地了，网关**永久失去返回干净 502 的能力** —— 只能给客户端一个半截的 200。保活改用 TCP 层（不产生应用层字节）。

这条是 **I1**，也是整个「失败只在网关内部消化」承诺的地基。

**排除了什么**：
- SSE 注释行心跳（`: keep-alive`、`\n\n` 空行保活）——**永久排除**，不是配置项。
- 「先回 200 再想办法」的任何变体。

**何时该翻案**：不翻案。**这是不变量，不是取舍。** 若某上游要求必须尽快回字节才能保活，正解是改上游交互方式，不是破坏 I1。

## D03 · 连通性测试必须发真实请求；删除后台定时主动健康检查（2026-10-13 · v0.1.0 起）

**决策**：
- 渠道「测试连通」**发送一次真实最小对话请求**（走完整鉴权 + 路由链路），**只在手动触发时**发，默认关闭自动探测。
- **删除**「后台定时主动健康检查」这个设计。健康状态**只由被动信号驱动**（真实业务请求的成功/失败）。

**为什么**：用户明确要求避免封号 —— 只用 `GET /v1/models` 或构造特征明显的垃圾请求探测，容易被风控判定为异常流量。定时主动探测还会**误杀低频但健康的渠道**，并自身触发风控。

判定口径：只看「是否拿到合法响应帧」，**不因内容质量判定失败**。401/403 归因为**密钥问题**（不是网络问题），提示重配，**不重试、不冷却其他渠道**。

**排除了什么**：定时 ping、`/v1/models` 探活、空请求探活、按响应内容质量判健康。

**何时该翻案**：上游提供官方的、明确的配额/健康查询接口，且确认不会被判定为异常流量时，可为**只读查询**单独开一条路径（仍不得替代真实请求测试）。

## D04 · 同层默认按声明顺序，自动权重默认关闭（2026-10-11 · v0.2.0）

**决策**：同 tier 内**按列表顺序**依次尝试；`auto_weight` 开关**默认关闭**，开启后才按权重降序（权重相同保持列表顺序）。

**为什么**：用户要的是**可预测**的降级顺序 —— 手工排好的梯队不该被权重悄悄打乱。权重仍照常存盘，可以先批量填好权重再一次性开启。

**排除了什么**：默认按权重调度（SWRR 平滑加权轮询仍保留为开启后的实现方式）。

**何时该翻案**：用户明确表示「默认就该按权重调度」时。改动只涉及默认值，不影响两种模式的语义。

## D05 · 退化输出「纠正续写」，而不是丢掉整段回答（2026-10-15 · 尚未发版）

**决策**：模型陷入复读时，**保留复读之前的正文**，对**同一个候选**发一次纠正请求（提示词写明「你在复读了，接着被打断的地方继续」），续写**接回同一条流**。只有纠正不可用（关闭 / 次数用尽 / 总超时不够 / 纠正后仍复读同一段）才就地截断 + 正常收尾。

**为什么**：旧行为是「整段丢弃 + 内部换候选」，代价是**用户已经读到的正文被白白扔掉**。用户口径是「保留正文 + 说明原因 + 接着写」。

**关键约束（改了会坏）**：
- 纠正**不是新的一次尝试** —— 它在同一次 attempt 内部发生，所以「尝试次数」语义不变；纠正次数单独记 `loop_continues`，日志显示「成功（已纠正复读）」。
- ★**纠正前必须有可续写的正文**：模型从第一个字符就复读时「续写」没有内容可续，此时仍走换候选 —— **绝不把复读碎片当成功回答发给客户端**。
- 截断必须**落库可见**（`loop_truncated`，日志「成功（已截断）」），不得伪装成完好回答（**I6**）。

**排除了什么**：把复读整段丢弃；把复读当成功外漏；为纠正而延长总超时预算（纠正受本次请求总超时约束）。

**何时该翻案**：上游开始提供**结构化**的重复/退化信号，或模型侧能在协议层自我纠正时。

## D06 · 密钥「存储分离」而不是加密（2026-10-14 · v0.4.2）

**决策**：密钥从 `config_json` 挪进独立的 `secrets` 表，`config_json` 里只留占位符 `__stored_in_secrets__`。

**为什么**：先解决「密钥明文散落在配置 JSON 里、导出/复制配置就带走密钥」这个具体问题，代价最小。

**★ 诚实边界（不许说成「已加密」）**：库里**仍是明文** —— 拿到 `gateway.db` 就能读。**DPAPI / OS 级加密仍未做。**

**兼容性约束（实现时必须保留）**：`load_config` **只替换值恰好等于占位符的字段**，手写/旧库的明文原样保留 ⇒ 老库无需重建。

**已知限制**：`ApiKey` 结构体没有 `id` 字段，网关密钥的 secret 键是 `api_key:<group_id>:<name>`，所以**同组同名**的两条 api_keys 会塌成一条。

**何时该翻案**：需要「磁盘被拿走也不泄密」时 —— 那时上 DPAPI（Windows）并把上面这条限制一并修掉。

## D07 · 界面时长用中文「秒」，接口契约保持毫秒（2026-10-14 · v0.4.4）

**决策**：界面**一律**显示中文「秒」（`0.03秒` / `1.4秒` / `12秒` / `4分30秒` / `2小时10分`）；「设置」与分组详情「重试与超时」的时长输入框按**秒**填。**接口契约不动** —— `retry.*_ms` / `duration_ms` / `ttft_ms` 字段名与默认值一个都没改，内部仍按毫秒存储（填 `0.5` = `500ms`）。

**为什么**：用户看不懂 `ms`。换算是**展示层**的事，不该渗透到接口。

**排除了什么**：把接口字段改名成秒、或改默认值 —— 会破坏既有配置与测试调用点。

**何时该翻案**：接口契约本身要重构时（那时同步改文档与全部测试调用点，是一次性动作）。

## D08 · `exposed_models` 由服务端按分组成员自动派生（2026-10-15 · 尚未发版）

**决策**：暴露模型列表**不再手填**，由服务端从各分组的成员**派生**；进程启动时重新派生并落库（`normalize_exposed_models`），`GET /v1/models` 同时列出派生名与分组名/id。

**为什么**：手填的列表会与实际成员**漂移** —— 删了成员、列表还留着，`/v1/models` 就会报出网关实际不认的模型名。

**关键语义（不许改坏）**：**精确名优先** —— 请求的模型名若命中某分组的 `exposed_models`，走**窄语义**（只调该模型绑定的候选），**不被同名分组截走**。

**何时该翻案**：需要「对外暴露名 ≠ 内部分组成员」的运营场景（例如同一组模型按客户分不同暴露名）时 —— 那时得引入独立的暴露层，而不是退回手填。

## D09 · 不引入 CI / GitHub Actions，用本机真机验收替代（2026-10-11 起至今）

**决策**：仓库**没有** `.github/`、没有 CI 工作流、没有 `check:privacy` 之类的脚本门禁。主门禁是 `cargo test --release`（本机）+ **真机验收探针**（真实 `gw-server.exe` + 真实 Tauri 客户端 + 真实数据面请求）。

**为什么**：核心承诺（I1 零字节、失败零外漏、提交后不重发）**只有在真实实例上跑真实字节流才能证伪** —— 纯单元测试证明不了。而这些探针需要 Windows + WebView2 + 本机网关，云端 CI 跑不出同等证据。

**★ 代价（必须承认）**：门禁是**本机手工触发**的，没有自动化兜底；「提交前是否跑过」靠纪律而不是靠流水线。

**排除了什么**：为了「有 CI」而搭一套跑不了真实验收的流水线 —— 那正是**假绿门禁**。

**何时该翻案**：探针能在无 GUI 环境稳定复现核心断言时，把**那部分**搬进 CI（例如 `cargo test --release` 与纯 HTTP 层的探针）；**GUI 真机验收仍留在本机**。

## D10 · 开发期探针与证据不入库（2026-10-11 起）

**决策**：`tools/` 下的 `_accept-*.mjs` / `_diag-*.mjs` / `_rel0*/` / `_shots/` 等**绝大多数不入库**，逐个登记进 `.gitignore`。入库的只有少数通用工具（`tools/start-client.mjs` / `start-server.mjs` / `shot.ps1` / `verify-window-state.mjs` 等）。

**为什么**：这些探针**硬编码了本机端点与真实密钥**，且是「本次验收」的一次性证据。入库会同时带来两个问题：**泄密**与**噪声**（`tools/` 曾有 200+ 文件）。

**代价**：探针**不随仓库分发** —— 别人 clone 后拿不到真机验收工具，只能按 [TESTING.md](TESTING.md) 自己写。这是**有意接受的代价**。

**何时该翻案**：某条探针被证明**长期复用**且**不含本机信息**时，把它改造成参数化工具再入库（`start-client.mjs` 就是先例）。

## D11 · 分组详情「冷却状态」页签用前端本地分片，不改成服务端分页（2026-10-14 · v0.4.6）

**决策**：分组详情三个页签里，**请求日志 / 切换日志走服务端分页**（`limit` + `offset`），**冷却状态走前端本地分片**；`GET /admin/api/health` **保持返回全量快照**。

**为什么**：该页要用全量冷却数据算「另有 N 条其它渠道的冷却未显示」；改成服务端分页会**破坏那个口径**（页面只看得到当前页，算不出「其它」）。

**代价**：冷却列表在数据量极大时仍是全量拉取 + 前端切片。

**何时该翻案**：`/admin/api/health` 能同时提供**总数**与分页行（`{rows, total}`）时，可改为服务端分页并保留「其它 N 条」的口径。

## D12 · 版本号四处同步 + sidecar 二进制入库（2026-10-11 起）

**决策**：一次发版的版本号要**同步改四处**：`server/Cargo.toml`、`client/src-tauri/Cargo.toml`、`client/src-tauri/tauri.conf.json`、**以及两份 `Cargo.lock`**；`client/src-tauri/binaries/gw-server-x86_64-pc-windows-msvc.exe`（sidecar）**入库**并随版本重建。

**为什么**：sidecar 入库让「clone + `pnpm tauri build`」就能产出完整安装包，不需要先手工构建服务端；漏改任一处的版本号会让产物名与代码里的版本对不上。

**排除了什么**：把 sidecar 当作构建产物不入库（会让新克隆的仓库无法直接打包）。

**何时该翻案**：引入自动化打包流水线，sidecar 能在构建时可靠产出时 —— 那时可以改为不入库，但**必须同时提供一键构建脚本**。

**踩过的坑**：曾有提交把**非规范构建产物**当 sidecar 提交（`4596cfa` 修正为规范 release 构建产物）。**sidecar 必须来自 `cargo build --release` 的产物**，不能随手拷一个 exe。

## D13 · `node_modules/.bin` 的 shim 不可用于脚本化构建（2026-10-14）

**决策**：批量/脚本化构建**直接调 JS 入口**（`node node_modules/vite/bin/vite.js` / `node node_modules/@tauri-apps/cli/tauri.js`），**不**走 `node_modules/.bin/*`。

落点是本机脚本 `tools/_build-client.sh`；**该脚本按 D10 不入库**（含本机路径），所以这条决策的**可复用部分只有「直接调 JS 入口」这条规则**，不是那个文件。

**为什么**：本机 bash **没有 coreutils**（无 sed / dirname / uname / tail），而 shim 需要它们。实测拿到过两种**假象**：一次**假的 `exit 0`**（末尾 echo 成功、构建其实没跑），一次 MODULE_NOT_FOUND —— 两次都像产品缺陷，实际是工具链问题。

**为什么记进决策**：它直接关系到**假绿门禁** —— 一个恒 `exit 0` 的构建脚本会让「构建成功」变成假象。

**何时该翻案**：构建环境提供了完整 coreutils（或改用 pnpm 脚本 + 确认退出码）时。

## D14 · 客户端数据目录：release 放 exe 同级，dev 放 target 下的 `data/`（2026-10-11 起）

**决策**：release 版把 `gateway.db` / `gateway.log` / `gateway.pid` 放在 **exe 同级目录**；debug 版放 `client/src-tauri/target/<profile>/data`。启动网关时**先探测 9090**，已有实例就不重复拉起。

**为什么**：release 要「安装完就在自己目录里自洽」，不写用户目录；dev 要**与已安装的正式版隔离**，避免调试时污染真实数据。

**相关实现约束**：记录 `gateway.pid`，使「退出（停止网关）」在**拉起它的进程已消失**时仍能停掉网关；杀进程前用 `tasklist` 校验**镜像名**，避免 Windows 回收 pid 后误杀别的程序。

**何时该翻案**：引入多实例/多用户场景时（那时需要显式实例隔离，而不是「exe 同级」）。

## D15 · 窗口状态记忆刻意排除 VISIBLE 与 DECORATIONS（2026-10-11 · v0.2.0）

**决策**：`tauri-plugin-window-state` 只记 SIZE + POSITION + MAXIMIZED + FULLSCREEN；**排除 VISIBLE**（且排除 DECORATIONS）。

**为什么**：窗口在**开机自启**与**关闭到托盘**时是隐藏的 —— 若把 `hidden` 持久化，下次手动启动会**看不见窗口**。排除 VISIBLE 还顺带避免插件在恢复时调 `show()` + `set_focus()`，让自启启动**安静地留在托盘**。DECORATIONS 排除是因为本应用从不切换装饰，留着只会多一条「状态文件过期导致标题栏消失」的路径。

**何时该翻案**：应用开始需要「上次退出时窗口是否可见」这个语义时（要另行设计，不能直接打开 VISIBLE）。

## D16 · 模型统计按「真实路由到的模型」聚合，不按客户端请求名（2026-10-15 · 尚未发版）

**决策**：模型维度的统计（`server/src/store.rs` 的 `stats_by_model`）按 `GROUP BY final_channel, final_upstream_model` 聚合，并给每行一个 `routed` 标志；`stats_by_group` 的「模型数」改成 `COUNT(DISTINCT final_channel || '::' || final_upstream_model)`。控制台所有「按模型」的图与表都用这一口径。**`exposed_model` 不再参与任何模型维度聚合。**

**为什么**：分组名与 id 本身就是可调用的模型名（见 [FEATURES.md](FEATURES.md) 的「分组名即模型名」）。客户端 `model: "<分组名>"` 请求时，`exposed_model` 存的就是分组名 —— 按它聚合会把一个分组的流量拆成 `grp_main` / `主力分组` 多行，**图里就把分组名当模型画出来**。实测（真机库，scope=all）：73 行里 10 行 / 537 次请求的 `exposed_model` 是分组名或 id；`grp_main` 68 次请求里 43 次落在别名行上，`by_group` 因此报 `models=4`（该组实际只有 3 个暴露模型）。

**配套语义（不许改坏）**：
- **行 = `上游模型 × 渠道`**，不是单个模型名 —— 同一个上游模型经多渠道路由时本就该分行（实测 `deepseek-v4.1-flash` 落在 7 个渠道上），图上重名时补渠道名区分。
- **从未路由成功的请求**（全渠道失败/耗尽，两个路由列都是 NULL）**单独一行** `routed: 0`，名字显示为「未路由（失败）」。刻意**不**丢弃它们：丢掉会让各行之和小于总数，等于把失败藏起来。SQLite 的 `GROUP BY` 把 NULL 归为一组，所以这天然就是一行。

**2026-10-15 修订（Owner 追加要求：失败也要按「渠道 - 具体模型」显示出来）**：上面那个「一行装下所有失败」的桶回答不了「**失败在哪个 渠道×模型 上**」。实测真机库 831 次请求里 **498 次没路由成功**，其中：
- **113 次真的尝试过候选**（82 次试 6 个、5 次试 3 个、24 次试 2 个）—— 这些尝试散落在 `switch_logs` 里，原先一行也没体现；
- **385 次一次都没试**（374 全冷却 `cooldown` + 11 无候选 `no_candidate`）= 全部失败的 **77%**，它们**没有渠道也没有模型**。

**Owner 裁决**：① 多候选失败**按每次尝试展开**（一个请求进多行）；② 0 次尝试的失败**单独一行**「未尝试任何渠道（全冷却 / 无候选）」。

**实现**：`stats_by_model` 改为三支 `UNION ALL` —— `routed`（request_logs 的 final_* 列）/ `attempted`（join `switch_logs`，按 request×pair 去重）/ `unrouted`（无任何 switch_log 行），每行带 `kind`。

**★ 两条刻意的代价（不许"修"）**：
1. **「请求数」各行之和会大于请求总数** —— 一次请求试了多个候选就进多行。这正是「按每次尝试展开」的语义。
2. **成本 / token 只记在 `routed` 行**：失败尝试的花费已由 `wasted_cost_usd` 表达，摊到尝试行会与分组总额重复计价。
- **请求日志的「暴露模型」列不动**：它回答「客户端要的是什么」，与统计口径是两件事。

**何时该翻案**：若将来统计要回答「客户端请求名维度」的问题，那是**新增一个维度**，不是把这一维改回去 —— 两个维度可以并存，但不能用一个冒充另一个。
