# 用户可见行为规格（FEATURES）

> 这里写**用户/调用方能看见的行为**：路由语义、分组、报错、统计口径、界面约定。

## 分组名即模型名

每个分组的**名称**和**id**本身就是一个可直接调用的模型名：用任意 OpenAI / Anthropic / Gemini 兼容客户端请求 `model: "<分组名>"`，网关就把该组所有层级的启用成员当成候选池，按层自动轮换与故障转移。

- **精确名优先**：如果请求的模型名正好出现在某个分组的 `exposed_models` 列表里，走的是窄语义（只调该模型绑定的候选），不会被同名分组截走
- `GET /v1/models` 同时列出 `exposed_models` 里的名字与各分组的名称/id
- 客户端「分组路由」页里每个分组都有一键复制的模型名提示
- 「渠道与模型」页可以从上游 `GET {base_url}/models` 拉取清单勾选导入，也可以手动填写（见下「添加模型」）

## 每个分组：跟随全局配置，或自己有配置

重试、超时、冷却等待、死循环拦截等预算默认继承全局（设置页的「重试与超时（全局默认）」）。策略配置跟着分组走：在「分组路由」页点某个分组的「分组详情」，页面顶部「分组设置」卡里的「重试与超时」区就是它自己的配置（内联编辑，改完点该卡的「保存设置」，再点顶栏「保存」落库），可以单独选择：

- **跟随全局配置**（默认）：改动全局值即时对该组生效
- **使用自己的配置**：该组用自己那份预算，可一键「复制全局配置」作为起点；服务端返回 `retry_source` 告知当前用的是哪一份

组级预算同样受 I4 约束（`max_attempts × attempt_deadline_ms + reserve_ms ≤ total_deadline_ms`），不合法的配置在保存时返回 400 且不会写入。

★ 从「自己的配置」切回「跟随全局」**不会销毁**已改动的那份：再切回来还是之前改过的值（存档只活在当前页面实例里，不落库）；只有在点「放弃修改」时才显式清空。

## 路由语义

- 分组内 tier 1 → 2 → … 升序尝试；同 tier 内**按列表顺序**依次尝试（默认）
- 自动权重（`auto_weight`，默认关闭）：开启后同 tier 内改为按成员权重降序，权重相同则保持列表顺序
- 成员的**顺序**和**权重**（数字输入框）在「分组路由 → 某个分组的「模型配置」卡」里改（就在分组详情页当前页面，不用跳页），开关的两种状态下都能改：关闭时权重照常存盘但暂不参与调度，开启后立即生效，可以先批量填好权重再一次性开启
- 排序两种方式等价：按住成员行首的抓手**拖动**，或用**上移 / 下移**按钮（键盘与读屏可用）；层头的抓手可以拖动**层级先后**，拖到哪一级，层级号就跟到哪一级
- 「模型配置」卡是独立的草稿：改完点卡上的「保存模型配置」写入本地配置，再点顶栏「保存」落库；卡上还有「放弃修改」，切换页签或不保存直接离开会保留草稿
- 候选失败 → 组内下一个；一级全冷却 → 下一级；末级也死 → 回到一级，循环 `max_cycles` 轮
- 全部冷却时 `cooldown_wait=true` 会等到最近一个冷却恢复再试（不白白失败）
- 健康 (channel × model) 粒度：401/403 整渠道隔离，404 只隔离该模型 6h，429/5xx 指数退避 15s→300s
- 提交点：流式请求在收到第一个合法内容帧后才向客户端写首字节（I1：提交前零字节），失败切换对客户端完全透明
- 中途断流：网关补 repair 帧（`gateway_upstream_interrupted`）+ 正常终止符，客户端永远拿到结构完整的响应

## 死循环输出拦截（loop guard）

模型陷入重复输出（死循环、无意义复读）时，网关**在内部**处理这次退化（默认开启）。
处置的核心不是「把这段回答整段丢掉」，而是**保留复读之前的正文、说明原因、让模型接着写**：

| 命中时机 | 处置 | 客户端看到什么 |
|---|---|---|
| **回答开始发送之前** | 切掉复读、保留正文，对**同一个候选**发一次纠正请求（提示词里写明「你在复读了，接着被打断的地方继续」），续写接回同一条流 | 一次正常回答，复读文本**零字节**外漏，复读前的正文**一个字都不丢** |
| **回答已经开始发送之后** | 同样切掉复读、保留正文并纠正，续写**接回同一条流**（无法重新开始：字节已经在客户端手里） | 一条连续的回答，复读前的正文一个字都不丢 |
| **纠正不可用时**（纠正关闭 / 次数用尽 / 总超时不够 / 模型复读同一段内容） | 就地截断 + 正常收尾 | 一条结构完整、正常结束的回答，但内容被截断；日志里记为「成功（已截断）」 |

纠正**不是新的一次尝试**：它发生在同一次尝试内部，所以「尝试次数」的语义不变，纠正次数单独记为 `loop_continues`，
日志状态显示为「成功（已纠正复读）」。★纠正前必须**有可续写的正文**：如果模型从第一个字符就在复读，
「续写」没有可续的内容，此时仍按旧路径换候选——绝不把复读的碎片当成成功回答发给客户端。

判定用滚动字符窗口上的 5 条规则（缓冲长度、重复次数、重复覆盖字符数、重复占比、单元不得是纯空白），阈值都在设置页可配。

★**空行分隔的复读另有兜底**：上面 5 条要求重复单元**连续贴在尾部**。但模型复读时常写成**两串、中间空一行、末尾再加一句总结**
（「（共 20 遍）」）——空行把两串切开、总结句又破坏了尾部对齐，这类形状原先**整段原样泄漏**给客户端（实测 144 字符）。
兜底规则（R6）只在前面 5 条全部落空后才跑：它要求判定范围内**必须含空行**，把空白折叠后重新找重复单元，并允许末尾最多 32 字符的
「结尾话」不属于重复；重复次数、覆盖字符数、占比这三条**门槛原样不变**。要求含空行，是为了让普通单行散文、markdown 小节标题、
表格行完全不受影响（34 例语料 + 12 字符帧步进实测：R6 在这些形状上零命中）。

★**为什么「开始发送之后」的判定只看末尾一小段**：规则里有一条要求重复部分占判定范围的 75%。若判定范围是整个 4000 字符窗口，那么复读要占满约 3000 字符才会被抓到 —— 模型从某一段开始复读时，用户的回答早就毁了。所以提交后判的是末尾一段（默认先 128、再放宽到 384，见下面的边界说明），语义变成「最近这段输出就是循环」。实测：400 帧的复读只泄漏 24 个单元（约 96 字符）；不检测时会泄漏 400 个单元（1720 字符）。

**诚实边界（不要期待超出这些范围）**：

- 只有**流式**路径检测：`stream: false` 一次拿到完整 JSON，没有增量帧，不检测
- 提交后命中**一定会泄漏一小段已经发出去的复读文本**（字节已在客户端手里，无法撤回），泄漏量由 `loop_guard_tail_chars` 与纠正轮数共同决定。
  这是物理限制，不是可以再优化掉的实现细节；调小它能拦得更早，但要求重复更完整。
  每次纠正都是一条**新的上游流**，新流同样要先攒够证据才允许再切，所以「反复复读且不收手」的模型每次纠正会多泄漏一个证据窗口；
  卡住判定（复读单元与上一轮完全相同 → 不再纠正）把它压回一次纠正。这条不等式钉在 `l13f` 里：`leaked <= (1 + loop_continues) * repeat_min_chars`
- 纠正会**多花一次上游调用**（默认最多 2 次），所以它受本次请求的总超时约束，绝不延长预算；模型在纠正后仍复读同一段内容时提前停止，不把次数用完
- 纠正提示词可在设置页配置（`{unit}` / `{repeats}` 两个占位符），留空使用内置中文提示词；提示词**必须说明为什么被打断**，否则模型容易重新开始或道歉
- 开启后首字节推迟 `min(min_chars 个字符, hold_max_ms)`（默认 64 字符 / 250ms，都可配）。**只按字符数等是不对的**：64 字符在 400 字符/秒 的模型上是 160ms，在 2 字符/秒 的模型上要 32 秒。`hold_max_ms` 把等待锁在时间上；到点先提交，后续内容交给提交后判定（阶梯仍兜底）
- 关掉它首字节立即返回，但退化不再被拦截
- 误判是可能的（长文里恰好出现高比例重复，例如连续空行或重复分隔线）；提交前命中只影响该次尝试，会被内部重试吸收；提交后命中会截断当前回答（因此 `loop_guard_tail_chars` 不宜设得过小）
- 兜底规则仍受「缓冲长度」约束：**短于 `min_chars`（默认 64）的形状不判定**。一个连 holdback 都装不满的回答不构成风险，为它增加误判面不划算
- ★**「开始发送之后」可检测的重复单元长度上限是约 314 个字符**（默认阈值下）。提交后走**逐级放宽的阶梯**判定，
  每级放宽判定范围的同时**抬高**要求的重复次数：`tail_chars` 128/4 次 → 上限 25；384/6 → 54；1152/8 → 128；窗口 4000/10 → 314。
  抬高门槛不是可选项：范围一放宽，规则里「重复占判定范围 75%」那条就更容易满足，多要的重复次数正是用来抵消它的
  （故障注入确认：把宽级的门槛降回 `max_repeats`，一段 8 副本的正常回答会被切掉）。
  实测（互异字符单元逐个长度扫）：单元 24～130 全部拦下，上限约 314。
  注意**超过上限时失败是整段、不是漏一部分**：一个 55 字符单元重复 400 次会原样送达 22000 字符，`loop_truncated=0`。
  改之前的上限是 25 —— 模型重复一段 **45 字符**的英文短句（真实案例：`Let me write./Here./Final./...` 重复 60 次）时**整段 3778 字符原样泄漏**；现在会在泄漏约 312 字符后截断。
  ★同一条长单元在**开始发送之前**仍会被拦下（那时判整个窗口，不只看尾部）——所以这个缺口只影响「回答已经开始发送之后」。
  再往上想扩大上限，就继续加宽判定范围、同时提高重复次数门槛；两者必须一起动，只放宽范围会让误判面变大。

## 思考（reasoning / thinking）透传

客户端发来的思考参数（OpenAI 的 `reasoning_effort`、`reasoning.effort`、
Anthropic 的 `thinking{type,budget_tokens}`、Gemini 的 `generationConfig.thinkingConfig`，
以及 DeepSeek/vLLM 系的 `reasoning_content`、`enable_thinking`/`extra_body`、Qwen/DashScope 形状）**会原样传给上游**；
上游回来的思考**单独**发给客户端（OpenAI `delta.reasoning_content`、Anthropic `thinking_delta`、Gemini `parts[].thought=true`），
**不会混进正文**。

- **同协议时原样回放**客户端自己的字段，跨协议才翻译（effort ↔ 预算 token 的映射写死在 `server/src/protocol/ir.rs`）。
- 客户端**没有**要思考的请求不会凭空多出字段；带工具调用、多模态、多轮对话的请求不受影响。
- 实测（回显上游）：修复前上游只收到 `keys=messages,model,stream`；现在三个思考参数全部到达。

**诚实边界**：

- 缓冲响应（`stream: false`）里 **Anthropic 的思考块会被丢弃**：Anthropic 校验思考块的 `signature`，
  而网关不携带签名，回放一个无签名块会把原本可用的下一轮请求变成 400。**流式路径照常透传**（`thinking_delta` 不需要签名）。
- 缓冲响应里 **OpenAI 的思考同样被丢弃**：不发明客户端没要的 `reasoning_content` 字段，避免改变客户端的消息解析。
  要拿思考就用流式。
- Gemini 缓冲响应**可以**带思考（不需要签名），所以它是三者里唯一在缓冲路径也透传的。
- 思考内容**不占用** holdback 缓冲：它一到就转发，不推迟首字节（见 loopguard-spec.md §2 关于计时起点的说明）。
- 思考内容**参与**死循环判定（`loop_guard_reasoning_enabled`，默认开）：模型在自己的思考里打转时永远走不到回答，
  而且思考会无上限地刷给客户端。判定用的是**同一个 `LoopGuard` 的同一套规则**，但是**另一个独立实例**——
  两路文本不混在一个滚动窗口里，所以「思考尾部 + 回答开头」这种接缝不会被误判成回答复读。
  代价是零：提交前的思考本来就要缓存（重试不能把已经想过的内容再放一遍给客户端），判定读的是本来就要缓的字节。
  提交后命中只是**停止继续转发思考**，回答照常发完——日志单独记 `reasoning_truncated`，不与 `loop_truncated` 混为一谈。
  真机验收（v0.4.7 发版，**在安装包解出的二进制上复跑**）：正常回答 5 字 / 门槛对照 64 字思考**全达** /
  思考打转被拦截（切换日志 `思考复读：…`）/ 唯一候选走诚实终态。分组详情页成员行渲染出「思考打转 1」徽章。

设计与验收细节：[loopguard-spec.md](loopguard-spec.md) · [reasoning-passthrough-spec.md](reasoning-passthrough-spec.md)。

## 报错文案与失败原因

- **所有面向调用方的报错都是中文**（用户看不懂英文报错）。`code` 标识符保持英文（`all_upstreams_failed` 等），供程序判断；
  只有给人看的 `message` 是中文。
- 失败消息**说明原因**，不只报次数：例如
  `上游 6 次尝试全部失败（原因：鉴权失败×3、被限流×3）。最后一条失败原因：上游返回 401：鉴权失败（API Key 无效或已过期）。请求 ID：…`。
  只有一种失败原因时只印那一条详情，不重复印一遍汇总。
- **请求日志页新增「失败原因」列**：直接显示 `error_message`（失败行为中文原因，成功行为 `—`，悬停看全文），
  不必再去切换日志里翻是哪条尝试、为什么失败。切换日志里每一行的 `message` 也是同一套中文文案。
- 失败类的**中文词表只有一份**（`store::error_class_label`）：控制台、切换日志、客户端消息共用，三处不会对同一个类给出不同说法。

## 添加模型：手动填写，或从上游 models 接口拉取

「渠道与模型」页的工具条和每张渠道卡片上都有**添加模型**入口，打开后是两种并列的方式：

- **手动添加**：自己填绑定 ID、暴露模型名、上游模型名，并选一个渠道（也能顺手改四类价格）
- **从 models 接口获取**：选渠道 → 点「获取模型列表」，网关用该渠道的 `base_url` + API Key 去请求上游 `GET {base_url}/models`，把返回的模型名列成清单，勾选后一键导入（暴露名 = 上游名，之后可再逐条改）

细节与边界：

- 拉取走服务端 `POST /admin/api/channel-models`，浏览器不直接碰上游；也支持只给草稿 `base_url` + `api_key`（渠道还没保存进配置时就能先探一次）
- 已在本渠道绑定过的上游模型显示「已存在」并不可勾选，不会重复导入
- 上游返回的模型列表带 `latency_ms`；清单过长会截断（响应里有 `truncated`）
- 失败一律可见地报在弹窗状态区（例如密钥错就是 `HTTP 401`），**不会**假装成功返回空列表
- 整段请求（连响应体）共用一个 20 秒超时，上游先回响应头再挂住 body 也不会让弹窗一直转圈

## 统计与请求日志

★ **模型口径 = 真实路由到的模型**（`final_upstream_model` × `final_channel`），**不是**客户端请求里写的模型名（`exposed_model`）。

为什么必须有这条：分组名与分组 id 本身就是可调用的模型名（见上「分组名即模型名」）。客户端用 `model: "<分组名>"` 请求时，请求名那一列存的就是分组名；若按它聚合，同一个分组的流量会被拆成 `grp_main` / `主力分组` 多行，**图里就把分组名当成模型画出来了**（实测 `grp_main` 68 次请求里 43 次落在这种别名行上，且「模型数」会虚报）。

- 「按模型请求数」「按模型 token 占比」「按模型 token 构成」「按模型成本」「分组用量 → 模型数」**全部**按真实路由口径聚合
- 同一个上游模型经多个渠道时**分行**（`模型 + 渠道` 才是完整身份）；图上重名时自动补渠道名以便区分
- **失败也按「渠道 - 具体模型」显示出来**（不藏起来）。每一行带一个**状态**列，三种状态一眼可分：
  | 状态 | 含义 | 渠道 / 模型 |
  |---|---|---|
  | **成功** | 请求提交到了这个 渠道×模型 | 都有 |
  | **未成功** | 请求**试过**这个 渠道×模型，失败了（该请求最终失败） | 都有 |
  | **未尝试** | 该请求**一次候选都没试**（全渠道冷却 / 无候选） | **都没有**，显示为「未尝试任何渠道（全冷却 / 无候选）」，**不冒充**任何模型名 |
- ★ **失败请求按「每次尝试」展开**：一次失败请求试过 6 个候选，就会出现在 6 行里（试过的渠道×模型各一行）。所以**「请求数」列各行之和会大于请求总数** —— 这是刻意的，不是 bug；那一列在含失败行时的语义是「落在该 渠道×模型的尝试次数」。
- ★ **成本 / token 只记在「成功」行**：失败尝试的花费由该请求的 `wasted_cost_usd` 单独表达；把它再摊到尝试行会与分组总额**重复计价**。所以「未成功」「未尝试」两行的 token 恒为 0。
- 请求日志里的**「暴露模型」列保持原样** —— 那一列回答的是「客户端要的是什么」，与统计口径是两件不同的事，不跟着改

统计页除了总览数字与「按模型成本」表，还有两张 ECharts 图（配色跟随界面主题 token，切换分组过滤时一起重绘）：

- **请求数 · 按模型**：横向条形图，按请求数降序取 Top 8，条尾直标数值；卡片右上角显示 `Top N / 共 M 个模型`
- **用量占比 · 按模型**：环形图（前 6 名 + 其余合成「其他 N 个」），右上角是合计 tokens，与接口数据加和一致

请求日志有两处入口——顶栏「日志」页的全局请求日志，以及「分组详情 → 请求日志」页签——两处字段一致，都给出每行的：**总耗时、首字 TTFT、TPS 速度、输入 / 输出 tokens**（TPS 与耗时列在同一条记录里可直接对照）。

界面上的**时长一律用中文「秒」显示**（`0.03秒` / `1.4秒` / `12秒` / `4分30秒` / `2小时10分`），不再出现 `ms`；「设置」与「分组详情 → 重试与超时」里的时长输入框也按「秒」填写，**内部仍按毫秒存储**（`retry.*_ms` 字段与接口契约不变，填 `0.5` 就是 `500ms`）。

TPS 口径是 `输出 tokens ÷ 解码耗时`，解码耗时 = 总耗时 − 首字耗时。**当解码窗口不足 200ms 时退化为按总耗时算**（此时 TTFT 几乎等于总耗时，相减会把噪声放大成虚高的速度），所以该列宁可偏低也不会虚高；缺数据（无耗时或无输出 tokens）显示 `—`。

## 时间范围筛选（用量 / 请求日志 / 切换日志）

★ 日志页、统计页、分组详情页的用量 / 请求日志 / 切换日志，**默认只显示最近 1 天**，并可切 1 / 2 / 3 / 7 / 14 / 30 天。

为什么默认 1 天：这几个界面回答的是「现在发生了什么」。默认不设范围时，一个跑了几周的库会把首屏铺满历史数据，而人最关心的往往是刚才那几笔。

- 服务端参数是 `days`（回溯天数，正整数）。**省略或 0 = 不设下限**，即整表 —— 这是加这个参数之前的行为，所以老调用方与老测试的结果完全不变。
- 同一个 `days` 同时收窄**三块聚合**（`summary` / `by_model` / `by_group`）与**两种日志的 `rows` 与 `total`**，所以「总数」和它下面的表永远描述同一个窗口。
- 筛选是**按天回溯**（`now - days`），不是自然日边界；`days=1` 是「最近 24 小时」。
- 时间比较走 `ts` 上的索引（字符串比较，因为 `ts` 是本机时区的 RFC3339 定长格式，字典序即时间序）；用 `julianday()` 虽然时区无关，但会让每次轮询都全表扫描。

★ **冷却状态页签不参与时间筛选**：它是「此刻正在冷却」的**实时快照**（字段只有渠道、上游模型、类型、到期时刻、连续失败次数），没有起始时间，也没有历史表 —— 「最近 1 天有哪些渠道被冷却过」这个问题当前的数据答不了，摆一个不生效的控件比不摆更误导。

★ 分组详情页的**概览页签**同样不显示范围选择器（概览里没有按时间聚合的数字），但它的页签计数**会**带上范围文案（「请求日志 N 条（最近 1 天）」），否则「0 条」会被读成「这个分组从没请求过」。

★ **日志不再显示「分组」列**（全局日志页的两个页签）。分组详情页本来就在页头标着分组，全局页删掉这一列后，定位靠**渠道 + 具体上游模型**——这正是「渠道 - 具体模型」的口径。日志页与统计页的「按模型成本」表都给出**实际调用的渠道与上游模型**，不再让人只知道分组、不知道是哪个渠道的哪个模型。

★ 修掉一个列错位：统计页「按模型成本」表**漏了「状态」表头**（6 个表头对 7 个单元格），整行右移一格，看起来就像「模型 = 未尝试、渠道 = 未尝试任何渠道」。补上表头后 `状态 / 模型 / 渠道 / …` 逐列对齐。

★ 分组详情页的三个页签（请求日志 / 切换日志 / 冷却状态）**各自分页**：前两者走服务端 `limit`+`offset`，冷却状态是前端本地分片（因为该页要用全量冷却算「另有 N 条其它渠道的冷却未显示」，改成服务端分页会破坏这个口径 —— 见 [DECISIONS.md](DECISIONS.md) D11）。页签右侧计数用**服务端返回的总数**，翻页时不变。

## 客户端界面约定

- **页面**：渠道（含透传 headers、连通测试=真实请求）、模型绑定（暴露名→上游名、四类价格，支持手动添加或从上游 models 接口勾选导入）、分组路由（分组卡片列表 + 分组详情：概览看板 / 用量统计 / 请求日志 / 切换日志 / 冷却 / 内联的「分组设置」；内联的「模型配置」卡管一级/二级/… 的成员顺序——拖动或按钮排序、与自动权重开关）、设置（重试/超时/监听/自启开关/自动权重/死循环拦截）、日志（切换日志按 `request_id` 过滤 + 请求日志，退化尝试标记为「输出退化」；时间范围默认 1 天，自动刷新默认开）、统计（总览 / 图表 / 按模型成本 / 冷却状态 / 死循环拦截次数）。
- **死循环拦截的界面口径**：命中「回答开始发送之前」时**在内部纠正续写**（复读文本零外漏）；命中「之后」时保留正文并纠正续写，纠正不可用才就地截断 + 正常收尾。日志里 `loop_truncated > 0` 显示「成功（已截断）」、`loop_continues > 0` 显示「成功（已纠正复读）」，**都不得只写「成功」**。代价是首字节推迟约 `loop_guard_min_chars`（默认 64）个字符——可配；提交后的判定只覆盖末尾 `loop_guard_tail_chars`（默认 128）个字符（见上「诚实边界」）。
- **密钥展示**：分组看板与分组详情页的「密钥」列表都只显示前 8 位，每行右侧有一个复制按钮，点它取回完整密钥（完整值只在点击那一刻从内存里取出，界面文本与 tooltip 里始终是脱敏串）。
- **侧栏**：可以折叠，折叠后 logo 与标题一起收起、整条只留一个展开按钮，展开恢复。
- **窗口**：记住上次的大小与位置；开机自启默认关闭，开启后静默驻留托盘。
- **界面通用规范**（设计令牌、通用组件、交互规范）见 [../client/UI-SPEC.md](../client/UI-SPEC.md)。
